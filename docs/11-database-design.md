# 数据库设计 — 通俗版

## 先搞清楚：这个项目为什么要有这7张表？

你可以把整个项目想象成一个**迷你版淘宝**，用户要能注册、登录、看商品、秒杀下单、付钱、取消订单。那最少需要存哪些数据？

```
用户信息 → t_user
商品信息 → t_product
秒杀活动 → t_seckill_activity
买了东西的订单 → t_order
订单里买了啥 → t_order_item
消息处理记录 → t_mq_message
每次库存变动记录 → t_stock_flow
```

就这7张，一张不多一张不少。下面我一张一张讲。

---

## 第一张：t_user（用户表）

### 这张表存什么？
就是用户的账号信息：用户名、密码、昵称、手机号。

### 什么时候用？
- **注册的时候**：往这张表里插一条新用户
- **登录的时候**：按用户名查这条记录，比对密码对不对
- **获取当前用户信息的时候**：按用户ID查这条记录

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每个用户的唯一编号，自增 |
| 唯一键 | uk_username | username | 用户名不能重复，两个人不能注册同一个用户名 |
| 普通索引 | idx_phone | phone | 按手机号查用户时加速 |

### 为什么用户名要唯一键？
因为高并发下，两个人可能同时注册同一个用户名。如果先查再插，两个人都查出来"没有这个用户"，然后都插入成功，就有两个一样的用户名了。

直接插，靠数据库唯一键拦住，撞了就报"用户名已存在"。

---

## 第二张：t_product（商品表）

### 这张表存什么？
商品的基础信息：标题、价格、库存、上下架状态、详情。

### 什么时候用？
- **商品列表**：查 status=1（上架中）的商品
- **商品详情**：按商品ID查这个商品的详情
- **新增商品**：插入一条新商品
- **修改商品**：按ID更新商品信息

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每个商品的唯一编号，自增 |
| 普通索引 | idx_status | status | 按上架状态查商品时加速 |
| 特殊字段 | version | - | 乐观锁版本号，防止两个人同时改同一个商品互相覆盖 |

### 为什么商品表和秒杀活动表要分开？
因为一个商品可以搞多场秒杀活动。比如iPhone 15：
- 双11秒杀价4999
- 双12秒杀价4799
- 年货节秒杀价4599

每一场活动的价格、库存、时间都不一样，所以不能存商品表里，要单独一张活动表。

---

## 第三张：t_seckill_activity（秒杀活动表）

### 这张表存什么？
每场秒杀活动的信息：关联哪个商品、秒杀价、总库存、活动时间、剩余库存。

### 什么时候用？
- **活动预热**：定时任务每分钟扫一遍，看看哪些活动快开始了，提前把库存预热到Redis
- **活动列表**：展示正在进行的秒杀活动
- **消费端下单**：Redis扣减成功后，这张表的剩余库存也要减1
- **订单取消**：取消订单后，这张表的剩余库存要加1
- **库存对账**：每5分钟拿这张表的库存和Redis库存比对

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每场活动的唯一编号，自增 |
| 普通索引 | idx_product_id | product_id | 按商品查活动 |
| 普通索引 | idx_start_end | start_time, end_time | 按开始结束时间查活动（预热任务用） |
| 普通索引 | idx_status | status | 按活动状态查活动 |
| CHECK约束 | ck_activity_stock_non_negative | available_stock >= 0 | 库存不能扣成负数，数据库层面兜底 |
| 特殊字段 | version | - | 乐观锁版本号 |

### total_stock 和 available_stock 有什么区别？
- **total_stock**：这场活动总共有多少件，永远不变（快照）
- **available_stock**：还剩多少件，有人买了就减，有人取消就加

对账的时候拿 total_stock 来算，看看 Redis 里的库存对不对。

---

## 第四张：t_order（订单表）— 最重要的一张表

### 这张表存什么？
用户买了什么东西的记录：订单号、谁买的、买了哪个活动、多少钱、订单状态。

### 什么时候用？
- **MQ消费下单**：往这张表里插一条新订单
- **查订单详情**：按订单号查这个订单
- **支付**：把订单状态从"待支付"改成"已支付"
- **超时关单**：把订单状态从"待支付"改成"已取消"
- **用户取消**：和关单一样，改状态
- **超时兜底扫描**：每分钟扫一遍哪些订单超时没支付

### 有什么键？
这张表有3个唯一键，是整个项目幂等的核心：

| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 订单ID，雪花ID |
| 唯一键 | uk_order_no | order_no | 订单号不能重复，防止重复下单 |
| 唯一键 | uk_user_activity | user_id, activity_id | 同一个用户同一个活动只能买一次（一人一单） |
| 唯一键 | uk_message_id | message_id | 同一条MQ消息只能消费一次，防止重复消费 |
| 普通索引 | idx_status_expire | status, expire_time | 超时关单兜底扫描用 |
| 普通索引 | idx_user_create | user_id, create_time | 用户订单列表查询 |
| 普通索引 | idx_activity | activity_id | 按活动查订单 |

### 为什么有3个唯一键？
因为可能出现3种重复：
1. 用户点了两次抢购 → 订单号重复 → uk_order_no 拦住
2. Redis出问题，同一个用户的请求漏过了 → uk_user_activity 拦住
3. MQ消息重复投递了 → uk_message_id 拦住

### 订单状态有几种？
```
0待支付 → 1已支付
       → 2已取消（超时没付或用户主动取消）
```

所有状态变更都用 `WHERE status=0` 条件更新，保证并发安全。比如支付和关单同时发生，只有一个能成功。

### product_title 和 seckill_price 为什么要存在订单表里？
因为商品可能改价。下单的时候把商品标题和价格存一份快照，后面商品改价了，已下单的价格不会变。

---

## 第五张：t_order_item（订单明细表）

### 这张表存什么？
订单里具体买了哪些商品，和订单表是一对多关系。

### 什么时候用？
- **下单时**：往这张表里插一条，记录这个订单买了哪个商品、多少钱、买了几件
- **查订单详情时**：按订单号查明细，展示买了啥

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每条明细的唯一编号，雪花ID |
| 普通索引 | idx_order_id | order_id | 按订单ID查明细 |
| 普通索引 | idx_order_no | order_no | 按订单号查明细 |

### 这张表是不是有点多余？
在秒杀场景下确实有点多余，因为一个订单就买一个商品，订单表里已经有 product_id 了。但留着它是为了扩展性——以后支持一个订单买多个商品时不用改表结构。

---

## 第六张：t_mq_message（消息记录表）

### 这张表存什么？
MQ消息的处理记录：这条消息是谁发的、消费成功了还是失败了、重试了几次。

### 为什么需要这张表？
因为 RabbitMQ 是"至少一次"投递，消息可能重复投递。消费者处理完了但ACK时网络断了，broker就会重投这条消息。如果不记录这条消息处理过没有，就会创建两个订单。

### 什么时候用？
- **消费消息时**：先往这张表里插一条记录（和订单创建在同一个事务里）
- **消费失败时**：更新这条记录的状态为失败，记录错误原因
- **生产消息失败时**：也写一条记录，方便排查

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每条记录的唯一编号，雪花ID |
| 唯一键 | uk_message_id | message_id | 同一条消息只能处理一次，重复投递时撞唯一键 |
| 普通索引 | idx_status_retry | status, retry_count, update_time | 失败消息重试扫描用 |
| 普通索引 | idx_biz | biz_type, biz_key | 按业务类型和业务键查消息 |

### 为什么必须和订单在同一个事务里？
如果分开：
```
先写消息记录（成功）
再开事务写订单（失败回滚）
    ↓
消息记录还在，但订单没创建
    ↓
消息重投 → 查到记录已存在 → 以为消费过了 → 直接跳过
    ↓
消息丢了，订单永远不会创建
```

所以消息记录必须和订单在同一个事务里，同生共死。

## 第七张：t_stock_flow（库存流水表）

### 这张表存什么？
每次库存变动的记录：谁的订单、扣减了还是回补了、变动前剩多少、变动后剩多少。

### 为什么需要这张表？
因为回补库存可能从多个入口触发：
1. 延迟队列超时关单 → 回补
2. 兜底扫描任务 → 回补
3. 死信消费者 → 回补
4. 用户主动取消 → 回补

如果两个入口同时回补同一个订单，库存就会多还一次 = 超卖。

### 什么时候用？
- **下单成功**：插一条"扣减"记录
- **订单取消**：插一条"回补"记录，如果撞唯一键说明已经回补过了，跳过

### 有什么键？
| 键类型 | 键名 | 字段 | 干什么用的 |
|--------|------|------|-----------|
| 主键 | PRIMARY | id | 每条流水的唯一编号，雪花ID |
| 唯一键 | uk_order_change | order_no, change_type | 同一个订单的"扣减"和"回补"各只能落一次 |
| 普通索引 | idx_activity_create | activity_id, create_time | 按活动查流水（对账用） |

### uk_order_change 怎么防重复回补？
它是 (order_no, change_type) 的组合唯一键：
- order_no=SO123, change_type=1（扣减）→ 第一次插成功
- order_no=SO123, change_type=2（回补）→ 第一次插成功
- order_no=SO123, change_type=2（回补）→ 第二次插撞唯一键 → 跳过

这样不管多少个入口同时回补，都只会成功一次。

## 7张表在业务流程里怎么串起来的？

### 第一步：注册登录
```
用户注册
  → INSERT t_user（新用户，uk_username 防重复）
    ↓
用户登录
  → SELECT t_user by username（查密码对不对）
    ↓
登录成功，拿到 JWT token
```

### 第二步：浏览商品
```
用户看商品列表
  → SELECT t_product where status=1（大部分被 Caffeine + Redis 缓存挡住，不碰DB）
    ↓
用户看商品详情
  → 先查 Caffeine → 再查 Redis → 都没有才 SELECT t_product by id
    ↓
商品不存在 → 写空值缓存（防穿透）
```

### 第三步：秒杀活动预热
```
定时任务每分钟跑一次
  → SELECT t_seckill_activity where end_time > now（找进行中/即将开始的活动）
    ↓
把活动库存、快照预热到 Redis
    ↓
预热完成 → 清 Caffeine 本地缓存（活动快照、售罄标记）
```

### 第四步：用户点抢购（不碰数据库）
```
用户点抢购
  → 查 Caffeine 活动快照（5秒TTL）
  → 查本地售罄标记（10秒TTL）
  → Redis Lua 脚本原子执行：
      ① 判断活动开始时间
      ② 判断库存够不够
      ③ 判断一人一单（SISMEMBER）
      ④ 扣减库存（DECR）
      ⑤ 加入已购集合（SADD）
      ⑥ 在途计数+1（INCR）
  → 以上全部在 Redis 里完成，不碰数据库！
    ↓
发 MQ 消息
    ↓
返回"已受理，排队中"
```

### 第五步：MQ消费创建订单（大事务，同时写5张表）
```
消费者收到消息，开一个大事务：
    ↓
① INSERT t_mq_message（消费记录，uk_message_id 幂等）
    ↓
② UPDATE t_seckill_activity SET available_stock = available_stock - 1
    ↓
③ INSERT t_order（订单，3个唯一键兜底幂等）
    ↓
④ INSERT t_order_item（订单明细）
    ↓
⑤ INSERT t_stock_flow（扣减流水，change_type=1）
    ↓
事务提交
    ↓
发 ACK
    ↓
事务提交后（不在事务里）：
  → 更新 Redis 秒杀结果为"成功"
  → 在途计数-1
  → 发延迟关单消息（30分钟后超时关单）
```

### 第六步：用户支付
```
用户点支付
  → SELECT t_order by order_no（查订单状态）
    ↓
UPDATE t_order SET status=1 WHERE order_no=? AND status=0
    ↓
影响行数=1 → 支付成功
影响行数=0 → 订单已取消，支付失败
```

### 第七步：订单超时关单（两条路径，互斥）
```
路径A：延迟队列（快）
  → 30分钟后消息进关单队列
  → UPDATE t_order SET status=2 WHERE order_no=? AND status=0
  → 如果影响行数=1：
      → UPDATE t_seckill_activity SET available_stock + 1
      → INSERT t_stock_flow（change_type=2回补，uk_order_change防重复）

路径B：兜底扫描（慢，每分钟一次）
  → SELECT t_order WHERE status=0 AND expire_time <= now
  → 对每个超时订单执行和路径A一样的关单逻辑
  → 两条路径同时关同一个订单，只有一个能成功（WHERE status=0）
```

### 第八步：死信补偿
```
消息重试3次还是失败 → 进死信队列
    ↓
死信消费者先查：
  → SELECT t_order by order_no
    ↓
订单存在？
  → 存在 → 不补偿（业务其实成功了，只是ACK断了）
  → 不存在 → 才补偿：
      → Redis 库存回补
      → Redis 已购集合移除用户
```

### 第九步：库存对账（每5分钟）
```
定时任务每5分钟跑一次
  → SELECT t_seckill_activity（读DB库存）
  → SELECT t_stock_flow by activity_id（读流水）
  → 读 Redis 库存、Redis 在途计数
    ↓
比对：Redis库存 == DB库存 - 在途数？
    ↓
不一致 → 告警或自动修复（Redis对齐到DB）
```

### 一张表出现的位置汇总

| 表 | 在哪些环节出现 | 操作 |
|----|--------------|------|
| t_user | 注册、登录 | INSERT / SELECT |
| t_product | 商品列表、商品详情 | SELECT（大部分被缓存挡住） |
| t_seckill_activity | 预热、下单、关单、对账 | SELECT / UPDATE |
| t_order | 下单、支付、关单、兜底扫描 | INSERT / UPDATE / SELECT |
| t_order_item | 下单 | INSERT |
| t_mq_message | MQ消费、失败记录 | INSERT / UPDATE |
| t_stock_flow | 下单扣减、关单回补、对账 | INSERT / SELECT |

## 唯一键汇总（幂等的核心）

| 唯一键 | 在哪个表 | 防什么重复 |
|--------|---------|-----------|
| uk_username | t_user | 两个人注册同一个用户名 |
| uk_order_no | t_order | 用户点两次抢购，创建两个订单 |
| uk_user_activity | t_order | 同一个用户重复买同一个活动 |
| uk_message_id | t_order | MQ消息重复投递，创建两个订单 |
| uk_message_id | t_mq_message | MQ消息重复消费，重复处理 |
| uk_order_change | t_stock_flow | 同一个订单被回补两次库存 |

## 设计要点总结

1. **金额用 DECIMAL，不用 FLOAT**（精度会丢）
2. **时间精确到毫秒**（超时关单要靠时间戳判断）
3. **高并发表用雪花ID**（订单、明细、流水、消息），低并发表用自增
4. **唯一键是最后一道防线**：Redis挡高频，数据库唯一键兜底
5. **索引不是乱建的**：每个索引都对应一个具体查询场景
6. **订单表存快照**：商品标题和价格下单时固定，后面改价不影响已下单
