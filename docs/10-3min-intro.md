# 高并发商城项目 — 3分钟口述稿（一段版）

我做的这个项目是一个高并发秒杀商城，技术栈是 Spring Boot、MyBatis-Plus、Redis、Caffeine、RabbitMQ 和 MySQL，核心解决秒杀场景下的超卖、缓存击穿和消息可靠性三个问题。

秒杀是最核心的模块，整个流程是用户点抢购之后，先查活动有没有开始，再查本地售罄标记，然后生成一个订单号，接着用 Redis 的 Lua 脚本在一个原子操作里完成库存校验、扣减、一人一单判断和在途计数加一，之后发 MQ 异步创建订单，最后返回已受理让用户轮询结果。这里我没有用分布式锁，因为 Lua 脚本本身就是原子执行的，性能比加锁好很多。在途计数记录的是 Redis 已经扣了但订单还没落库的数量，用来做后面的库存对账。

缓存方面我用的是 Caffeine 加 Redis 的两级缓存，Caffeine 是本地缓存纳秒级，Redis 是分布式缓存毫秒级。缓存击穿用互斥锁加逻辑过期来解决，逻辑过期就是 key 不物理删除，过期后立刻返回旧数据同时异步重建，用户完全无感知。缓存穿透用 Redis 布隆过滤器加空值缓存来挡。缓存一致性用 Cache Aside 模式，写库之后删缓存，再加延迟双删防止并发竞态。

MQ 这块我从三个层面保证可靠性。发送端有三重保障：发送异常立刻补偿、Confirm 和 Return 双回调、还有定时任务每两秒扫描超时未确认的消息。消费端手动 ACK，区分五种结果，可重试的投到延迟重试队列等五秒再回来，避免零间隔自旋。死信消费者先查数据库订单是否存在，存在就不补偿，因为消息进死信不代表业务失败，无脑回补会超卖。补偿还有三层防重：先查订单、Redis SETNX 守卫、Lua 脚本库存封顶。

另外登录用令牌桶限流，商品详情和秒杀用滑动窗口限流。认证用 JWT 加 Redis 黑名单，按 jti 拉黑而不是 userId。订单超时关单用 RabbitMQ 延迟队列，三十分钟后条件更新关单。最后每五分钟跑一次库存对账，以数据库为准对齐 Redis，是最终一致性的最后一道防线。
