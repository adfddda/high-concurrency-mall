## 项目一　分布式交易系统（秒杀 · 库存一致性 · 可靠消息）

**项目简介：** 独立设计并实现一套交易系统，覆盖**秒杀（直接抢 + 预约抽签双模式）、普通下单（SKU / 购物车 / 优惠券 / 拼团）、支付与退款、履约、风控、网关与可观测**完整链路。核心命题是「瞬时并发远超数据库承载能力」时的正确性：用「本地内存 → Redis Lua 原子扣减 → MySQL 约束兜底」三级漏斗把流量挡在数据库之外，用「补偿 + 幂等 + 对账」三层机制把最终一致性收敛到可验证的状态。**17 张表 / 48 个 REST 接口 / 约 1.2 万行 Java（9.5k 业务 + 2.2k 测试 + 0.4k 网关）/ 96 个业务测试 + 5 个网关测试全绿**，CI 每次提交都拉起真实 MySQL / Redis / RabbitMQ / Elasticsearch 跑全量用例。

### 核心实现

**1. 三级漏斗与 Lua 原子扣减：把"不超卖"从业务逻辑降级为物理约束**

秒杀第一级在 JVM 内用 Caffeine 缓存活动快照并维护"本地售罄标记"，命中即拒绝、完全不访问 Redis；第二级把「库存校验 + 扣减 + 一人一单去重 + 资格码消费 + 在途计数」封装进**单个 Lua 脚本**原子执行——相比分布式锁省掉两次网络往返，也没有锁超时、看门狗续期、误删他人锁这一整类问题；第三级由 MySQL 条件更新 `WHERE available_stock >= ?` 与 `CHECK` 约束兜底，**Redis 只是可重建的准入闸门，权威库存永远在数据库**。为多 key 引入 Hash Tag `{act:N}` 保证集群同槽，并自实现 CRC16-XMODEM（用标准校验值交叉验证），把"集群可用"从口头承诺变成单元测试 + 启动期自检。

**2. 可靠消息：Confirm 不等于路由成功，"进死信"也不等于业务失败**

生产侧 `publisher-confirm-type=correlated` + `mandatory=true`，同时处理 Confirm 与 Return——Confirm 只表示 broker 收下了，**不保证进队列**，routingKey 写错时 broker 会 ack 后直接丢弃；再叠加投递台账与超时扫描，覆盖"broker 静默失联、Confirm 永不返回"。消费侧手动 ACK，把结果显式分五类（幂等命中 ACK / 唯一键冲突补偿后 ACK / 不可重试进死信 / 瞬时故障走 TTL 重试队列 / 重试耗尽进死信），避免毒丸消息。死信消费者**先查订单是否已落库再决定是否回补**——消息可能已成功建单、只在 ACK 那刻断连，无条件回补就是"订单在、库存也还回去了"的超卖。

**3. 补偿三层防重 + 对账：宁可少卖，绝不超卖**

补偿的五个入口（发送异常 / Confirm nack / Return / 超时扫描 / 死信）都可能重复触发：一层在补偿前确认订单确实不存在；二层用 `SETNX` 守卫保证同一消息只补偿一次；三层在 Lua 内用 `total_stock` 封顶。所有单点判断失误的后果都被限制在"少卖"（可修复）而非"超卖"（资损）一侧。此外实现周期性对账，维护不变式「Redis 库存 = DB 库存 − 在途数」。关键洞察是：**在途计数既是修正项，也会掩盖故障**——进程在"已扣未落库"时崩溃，库存少 1、在途多 1，两者相抵 drift 仍为 0。破局点在于在途是瞬态量，因此**连续 3 次采样都看到在途 > 0 等价于发现泄漏**，此时把 Redis 对齐数据库并清零。

**4. 多级缓存：把"不一致窗口"量化，而不是声称"已解决"**

Caffeine（L1，3s）+ Redis（L2，逻辑过期）两级缓存。穿透用「参数校验 + 布隆过滤器 + 空值缓存」三层；击穿用两套**互补**机制——热 key 到期走逻辑过期（返回旧值 + 异步重建，用户零等待），冷 key 缺失走 Redisson 互斥锁 + 双重检查（没抢到锁的请求短暂自旋等回填，而不是直接查库，否则加锁只保护了一个请求）；雪崩用物理 TTL 随机抖动打散。写入遵循 Cache Aside 且**先更新库、再删缓存**，删除通过 `@TransactionalEventListener(AFTER_COMMIT)` 推迟到提交之后（否则并发读会把旧值回填且长期无人修正），再叠 500ms 延迟双删。`l1-ttl` 就是多实例部署下的不一致窗口上界——**承认它，而不是假装没有**。

**5. 两套下单链路共存：按场景选架构，而不是把高并发方案套到所有写路径**

秒杀走「Redis 预扣 → MQ 削峰 → 异步落库」，用户拿到"排队中"并轮询结果；普通下单走「条件 UPDATE 扣 SKU 库存 → 写订单 → 核销券」的同步事务，点一下就能看到订单号。前者要吞吐，后者要确定性。这个对照本身就是设计的一部分：**很多项目把"高并发"当信仰，让普通下单一并去轮询结果**。

**6. 交易闭环：状态机与幂等用同一套方法贯穿到底**

订单 `CREATED → PAID → SHIPPED → FINISHED`，旁支 `CANCELED` / `REFUNDED`，所有迁移都是「带前驱条件的 UPDATE + 影响行数判定」，因此"用户确认收货"与"定时任务自动确认"并发时只有一个赢家。支付单独建 `t_payment`（一个订单可能多次支付尝试，且回调幂等需要 `paymentNo` 粒度）：重复回调幂等成功、金额不一致直接拒绝。退款挂在**状态流转成功**的分支上，保证"重复退款不会多还库存"。优惠券沿用同一思路：发券用 `issued_count < total_count` 条件自增防超发，核销用 `status = 0 AND user_id = ?` 保证一券一单，退款/取消按订单号还券。

**7. 削峰三件套：限流挡"量"、风控挡"人"、抽签把"抢"变成"抽"**

网关层用 Redis 固定窗口做粗粒度保护（fail-open，`X-RateLimit-*` 头），业务层保留用户/接口维度的滑动窗口与令牌桶——**两个层次用不同精度，刻意不一致**。设备维度风控识别"一台设备 100 个账号"这类限流挡不住的黄牛：检查是只读的，**只有扣减成功才占用设备名额**（否则"没抢到还把你拉黑"），拦截落库可统计。抽签模式把"10 万人抢 200 件"变成"10 万人抽签 + 200 人凭码下单"：资格码镜像到 Redis，在扣减 Lua 里用 `SREM` 完成"校验 + 消费"，**同一个码不可能用两次**；库存检查放在消费资格码之前，避免中签者手慢一步连资格都被吃掉。

**8. 可观测：每个关键设计都必须有一个可观测信号**

业务埋点覆盖秒杀各分支占比、Lua 耗时分布、缓存各层命中、MQ 全链路事件、库存漂移、风控拦截，并区分「限流拒绝」与「限流组件降级」。Prometheus + Grafana 看板 8 个面板，每个直接对应一个设计决策（秒杀结果分布回答"流量卡在哪层"，缓存层级回答"是否真挡住 DB"，Lua P99 回答"Redis 是否瓶颈"）。接入 OpenTelemetry + Jaeger，`traceId` 贯穿 HTTP → MQ → 消费端并打进日志，MQ observation 打开后**一条消息在链路图里是连续的**。

### 效果验证

- **并发正确性（96 个业务测试 + 5 个网关测试全绿）：** 800 虚拟线程抢 200 库存，成功次数**恰好 200**、剩余库存**恰好 0**；同一用户 500 并发仅 1 次成功；重复回补 5 次被总库存封顶；200 并发打 limit=20 **恰好放行 20 个**；同一消息消费两次只产生一个订单；**重复退款不会多还库存**；**取消后可以重新抢**（唯一索引 + Redis 资格双释放）。
- **缓存效果：** 10 万请求压商品详情，**L1 命中 99.9%、L2 0.1%、数据库 0 次访问**。
- **吞吐：** 单机自压 **13,102 QPS**、服务端平均 **1.118ms**；因客户端与服务端同机争抢 CPU，该数字是**下界**。
- **故障降级：** RabbitMQ 完全不可用 + 2 万并发，5 个活动全部 `drift = 0`、在途归零，零库存泄漏；代价是 P95 从毫秒级劣化到 2 秒（已如实记录）。
- **工程化：** CI（GitHub Actions）每次提交拉起真实 MySQL / Redis / RabbitMQ / Elasticsearch 跑 `mvn verify`，同时构建业务镜像与网关镜像；**构建失败 = 门禁失败**。
- **一项被数据纠正的判断：** 首版用 Python 压测只测到 738 QPS，而服务端平均耗时仅 1.68ms——瓶颈全在压测客户端的 GIL。改用 Java 21 虚拟线程客户端后同机同接口 **13,102 QPS，相差 17.7 倍**。由此固化纪律：**报 QPS 之前先证明瓶颈不在客户端**。

3. **效果验证** 必须放数字，且每个数字都能被追问到底。**宁可少写一个，也不要写一个讲不清来源的。**

## 面试官最可能追问的 10 个点

| 追问 | 应对要点 |
|---|---|
| "怎么保证不超卖？" | 三级漏斗 + **给测试证据**（800 并发抢 200，成功数恰好 200），别只讲原理 |
| "Redis 和 MySQL 不一致怎么办？" | 补偿三层防重 → 对账兜底 → **在途计数既修正也掩盖故障**这个洞察 |
| "为什么不用分布式锁？" | 往返次数对比 + 锁自身风险清单 + "什么时候我会用锁" |
| "MQ 挂了会怎样？" | 直接给演练数据（2 万并发、drift 全 0），并主动说代价（P95 劣化到 2 秒） |
| "缓存一致性怎么保证？" | 先更库再删缓存 → AFTER_COMMIT → 延迟双删，**主动给出不一致窗口上界（3 秒）** |
| "你这 QPS 可信吗？" | 主动坦白单机自压、客户端抢 CPU，说明为什么是下界、怎么测真实容量 |
| "为什么一个项目里有两套下单链路？" | 吞吐 vs 确定性的取舍；**不要给所有写路径套 MQ** |
| "抽签/风控怎么做的？" | 资格码在 Lua 里 `SREM` 原子消费；设备名额只在扣减成功后占用（防误伤） |
| "这个架构有什么问题？" | 主动说：单机 Redis、L1 多实例不一致、内存台账不如 Outbox、K8s 清单未上真实集群验证 |
| "如果重做你会改什么？" | Canal 做缓存失效与索引同步、库存分桶 + Redis Cluster、订单按 user_id 分片、全链路压测 |
