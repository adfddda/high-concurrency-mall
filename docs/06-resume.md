## 项目一　高并发秒杀系统（商品 + 秒杀）

**项目简介：** 独立实现商品浏览与限时秒杀系统，核心命题是「瞬时并发远超数据库承载能力」时的正确性：用「本地内存 → Redis Lua 原子扣减 → MySQL 约束兜底」三级漏斗把 99.9% 流量挡在数据库之外，用「补偿 + 幂等 + 对账」三层机制把最终一致性收敛到可验证的状态。在标准秒杀之上扩展了**三种抢购形态**（直接抢 / 预约抽签 / 库存分桶）与**设备维度风控**。**10 张表 / 31 个接口 / 约 10,000 行 Java（业务 7,803 + 测试 1,835）+ 网关 / 84 个自动化测试全绿**，CI 每次提交都拉起真实 MySQL / Redis / RabbitMQ / Elasticsearch 跑全量用例。

### 核心实现

**1. 三级漏斗与 Lua 原子扣减：把"不超卖"从业务逻辑降级为物理约束**

第一级在 JVM 内用 Caffeine 缓存活动快照并维护"本地售罄标记"，命中即拒绝、完全不访问 Redis；第二级把「库存校验 + 扣减 + 一人一单去重 + 资格码消费 + 在途计数」封装进**单个 Lua 脚本**原子执行——相比分布式锁省掉两次网络往返，也没有锁超时、看门狗续期、误删他人锁这一整类问题；第三级由 MySQL 条件更新 `WHERE available_stock >= ?` 与 `CHECK` 约束兜底，**Redis 只是可重建的准入闸门，权威库存永远在数据库**。为多 key 引入 Hash Tag 保证集群同槽，并自实现 CRC16-XMODEM（用标准校验值交叉验证），把"集群可用"从口头承诺变成单元测试 + 启动期自检。

**2. 可靠消息：Confirm 不等于路由成功，"进死信"也不等于业务失败**

生产侧 `publisher-confirm-type=correlated` + `mandatory=true`，同时处理 Confirm 与 Return——Confirm 只表示 broker 收下了，**不保证进队列**；再叠加投递台账与超时扫描，覆盖"broker 静默失联、Confirm 永不返回"。消费侧手动 ACK，把结果显式分五类（幂等命中 / 唯一键冲突 / 不可重试 / 瞬时故障走延迟重试 / 重试耗尽进死信），避免毒丸消息。死信消费者**先查订单是否已落库再决定是否回补**——消息可能已成功建单、只在 ACK 那刻断连，无条件回补就是"订单在、库存也还回去了"的超卖。

**3. 补偿三层防重 + 对账：宁可少卖，绝不超卖**

补偿的五个入口（发送异常 / Confirm nack / Return / 超时扫描 / 死信）都可能重复触发：一层在补偿前确认订单确实不存在；二层用 `SETNX` 守卫保证同一消息只补偿一次；三层在 Lua 内用 `total_stock` 封顶。所有单点判断失误的后果都被限制在"少卖"（可修复）而非"超卖"（资损）一侧。此外实现周期性对账，维护不变式「Redis 库存 = DB 库存 − 在途数」。关键洞察是：**在途计数既是修正项，也会掩盖故障**——进程在"已扣未落库"时崩溃，库存少 1、在途多 1，两者相抵 drift 仍为 0。破局点在于在途是瞬态量，因此**连续 3 次采样都看到在途 > 0 等价于发现泄漏**。

**4. 多级缓存：把"不一致窗口"量化，而不是声称"已解决"**

Caffeine（L1，3s）+ Redis（L2，逻辑过期）。穿透用「参数校验 + 布隆过滤器 + 空值缓存」三层；击穿用两套**互补**机制——热 key 走逻辑过期（返回旧值 + 异步重建），冷 key 走 Redisson 互斥锁 + 双重检查（没抢到锁的请求短暂自旋等回填，而不是直接查库，否则加锁只保护了一个请求）；雪崩用物理 TTL 随机抖动打散。写入遵循 Cache Aside 且**先更新库、再删缓存**，删除通过 `@TransactionalEventListener(AFTER_COMMIT)` 推迟到提交之后，再叠延迟双删兜住更窄的窗口。`l1-ttl` 就是多实例部署下的不一致窗口上界——**承认它，而不是假装没有**。

**5. 削峰的两种形态：抽签把"抢"变成"抽"，风控把"量"换成"人"**

预约抽签把「10 万人抢 200 件」变成「10 万人抽签 + 200 人凭码下单」：资格码镜像到 Redis，扣减 Lua 用 `SREM` 在**同一个原子操作**里完成"校验 + 消费"，同一个码不可能用两次；库存检查放在消费资格码之前，避免中签者手慢一步连资格都被吃掉。设备风控解决限流挡不住的那类黄牛（一台设备 100 个账号）：**检查只读、扣减成功后才占用设备名额**（否则"没抢到还把你拉黑"），拦截落库可统计。

**6. 单 key 热点的解法：库存分桶（可配置、且有明确边界）**

单个活动库存是天然热点，Cluster 下只落一个分片，加机器也救不了。`SECKILL_BUCKETS > 1` 时按 `floorMod(hash(userId), N)` 拆桶，每桶用自己的 Hash Tag 落不同槽。三个代价写进了文档：桶间负载由哈希决定不可控、不做跨桶回退（会少卖不会超卖）、**单机 Redis 上没有吞吐收益**。默认关闭，行为与不分桶完全一致——不把没跑过的性能数字写进 README。

**7. 工程化：每个关键设计都有一个可观测信号**

业务埋点覆盖秒杀各分支占比、Lua 耗时、缓存各层命中、MQ 全链路事件、库存漂移、风控拦截。Prometheus + Grafana 看板 8 个面板，每个直接对应一个设计决策；OpenTelemetry + Jaeger 让 `traceId` 贯穿 HTTP → MQ → 消费端。CI 三个 job（全量测试 / 业务镜像 / 网关镜像），网关层用 Redis 固定窗口做粗粒度保护，与之互补的是业务侧的滑动窗口/令牌桶——**两个层次用不同精度，刻意不一致**。

### 效果验证

- **并发正确性（84 个测试全绿）：** 800 虚拟线程抢 200 库存，成功次数**恰好 200**、剩余库存**恰好 0**；同一用户 500 并发仅 1 次成功；重复回补 5 次被总库存封顶；200 并发打 limit=20 **恰好放行 20 个**；同一消息消费两次只产生一个订单；**取消后可以重新抢**（唯一索引 + Redis 资格双释放）；4 个库存桶下 800 并发仍恰好 200 成功。
- **缓存效果：** 10 万请求压商品详情，**L1 命中 99.9%、L2 0.1%、数据库 0 次访问**。
- **吞吐：** 单机自压 **13,102 QPS**、服务端平均 **1.118ms**；因客户端与服务端同机争抢 CPU，该数字是**下界**。
- **故障降级：** RabbitMQ 完全不可用 + 2 万并发，5 个活动全部 `drift = 0`、在途归零，零库存泄漏；代价是 P95 从毫秒级劣化到 2 秒（已如实记录）。
- **工程化：** CI 每次提交拉起真实 MySQL / Redis / RabbitMQ / Elasticsearch 跑 `mvn verify`；构建失败即门禁失败。
- **一项被数据纠正的判断：** 首版用 Python 压测只测到 738 QPS，而服务端平均耗时仅 1.68ms——瓶颈全在压测客户端的 GIL。改用 Java 21 虚拟线程客户端后同机同接口 **13,102 QPS，相差 17.7 倍**。由此固化纪律：**报 QPS 之前先证明瓶颈不在客户端**。

### 技术栈

Java 21（虚拟线程）、Spring Boot 3.5、Spring Cloud Gateway、MyBatis-Plus、MySQL 8.0、Redis（Lettuce + Lua）、Redisson、Caffeine、RabbitMQ（Spring AMQP）、Elasticsearch 8、springdoc / OpenAPI 3、Micrometer + Prometheus + Grafana、OpenTelemetry + Jaeger、Docker / Compose、Kubernetes、JUnit 5、k6。

## 面试官最可能追问的 8 个点

| 追问 | 应对要点 |
|---|---|
| "怎么保证不超卖？" | 三级漏斗 + **给测试证据**（800 并发抢 200，成功数恰好 200） |
| "Redis 和 MySQL 不一致怎么办？" | 补偿三层防重 → 对账兜底 → **在途计数既修正也掩盖故障**这个洞察 |
| "为什么不用分布式锁？" | 往返次数对比 + 锁自身风险清单 + "什么时候我会用锁" |
| "MQ 挂了会怎样？" | 直接给演练数据（2 万并发、drift 全 0），并主动说代价（P95 劣化到 2 秒） |
| "缓存一致性怎么保证？" | 先更库再删缓存 → AFTER_COMMIT → 延迟双删，**主动给出不一致窗口上界（3 秒）** |
| "你怎么削峰？" | 抽签（降请求量）+ 风控（挡黄牛）+ 分桶（散热点），三种形态解决三个不同问题 |
| "分桶为什么默认是 1？" | 单机 Redis 单线程，分桶没有收益；**只有 Cluster 下才有效**，且会少卖不会超卖 |
| "这个架构有什么问题？" | 主动说：单机 Redis、L1 多实例不一致、内存台账不如 Outbox、K8s 清单未上真实集群 |
