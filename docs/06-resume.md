## 项目一　高并发商城交易系统

**项目简介：** 面向商城商品浏览与限时秒杀场景，独立实现用户认证、商品多级缓存、库存预热、抢购下单、订单查询与超时关单的完整交易链路。以「**本地内存判断 → Redis Lua 原子扣减 → MySQL 条件更新兜底**」三级漏斗把 99.9% 的流量挡在数据库之外；通过 RabbitMQ 将抢购请求与订单落库解耦，并以「补偿 + 幂等 + 对账」三层机制保证 Redis 与 MySQL 的最终一致。Java 21 独立实现，约 7500 行代码（含 43 个自动化测试），配套 Docker Compose 一键环境、Java 虚拟线程压测客户端与完整设计文档。

### 核心实现

**1. 三级漏斗与 Lua 原子扣减：把超卖的可能性从"业务逻辑"降级为"物理约束"**

秒杀的本质矛盾是瞬时并发远超数据库承载能力。第一级在 JVM 内存里用 Caffeine 缓存活动快照并维护"本地售罄标记"，命中即拒绝且完全不访问 Redis；第二级把「库存校验 + 库存扣减 + 一人一单去重 + 在途计数」四步封装进**单个 Lua 脚本**，利用 Redis 单线程特性实现不可打断的原子执行——相比分布式锁方案省掉两次网络往返，也没有锁超时、看门狗续期、误删他人锁这一整类问题；第三级由 MySQL 的 `UPDATE ... WHERE available_stock >= ?` 条件更新与 `CHECK (available_stock >= 0)` 约束兜底，**Redis 只作为可重建的准入闸门，权威库存始终在数据库**。此外为多 key 引入 Hash Tag `{act:N}` 保证脚本在 Redis Cluster 下同槽，并自实现 CRC16-XMODEM（用标准校验值 `0x31C3` 交叉验证）把"集群可用"从口头承诺变成单元测试与启动期自检。

**2. 可靠投递与消费幂等：用"判断依据必须是数据库真实结果"代替"消息进死信就等于失败"**

生产侧配置 `publisher-confirm-type=correlated` 与 `mandatory=true`，同时处理 ConfirmCallback 与 ReturnCallback——因为 Confirm 仅表示 broker 收下了，**不保证路由到队列**，routingKey 写错时 broker 会 ack 后直接丢弃；再叠加内存投递台账与超时扫描，覆盖"broker 静默失联导致 Confirm 永不返回"的场景。消费侧采用**手动 ACK**，把结果显式区分为幂等命中（ACK）、订单唯一键冲突（补偿后 ACK）、不可重试失败（补偿后进死信）、瞬时故障（投递到 TTL 延迟队列重试）与重试耗尽（nack 进死信）五类，避免"一条永远失败的消息反复占用消费者"的毒丸问题。死信消费者**先查订单是否已落库再决定是否回补**——死信不等于业务失败，消息可能已成功建单、只是在 ACK 那一刻断了连接，无条件回补就会造成"订单在、库存也还回去了"的超卖。

**3. 补偿的三层防重与"宁可少卖绝不超卖"**

补偿逻辑是本项目最容易出错的一段：重复执行导致超卖，漏执行导致少卖。第一层在补偿前**先确认订单确实不存在**（否则 Confirm 超时与订单已创建会同时成立）；第二层用 Redis `SETNX` 守卫保证同一消息的补偿只执行一次（发送异常、nack、return、超时扫描、死信消费五个入口都可能触发）；第三层在 Lua 内用 `total_stock` 封顶，即使前两层都被绕过，库存也不会超过总量。三层叠加后，任何单点判断失误的后果都被限制在"少卖"这一可修复的一侧，而不会变成"超卖"这一资损的一侧。

**4. 最终一致性：用"在途计数泄漏探测"覆盖补偿逻辑够不到的场景**

所有补偿逻辑都建立在"进程还活着、代码没 bug"的前提上。为兜住这个前提之外的故障（进程崩溃、补偿失败、有人直接改 Redis），实现了周期性对账任务，维护不变式「稳态下 Redis 库存 == DB 剩余库存」与「有在途时 Redis 库存 == DB 剩余库存 − 在途数」。这里的关键洞察是：**在途计数既是修正项，也会掩盖故障**——进程在"已扣减、未落库"时崩溃，库存少 1、在途多 1，两者相减恰好抵消，单纯比对库存根本发现不了。破局点在于在途是瞬态量（正常只有几十毫秒），因此**连续多次采样都看到在途 > 0 就等价于发现了泄漏**，此时强制把 Redis 对齐到数据库并清零在途。修复方向始终是"Redis 对齐 DB"，因为数据库是唯一能自我保证正确性的一层。

**5. 多级缓存与 Cache Aside 一致性，并把"不一致窗口"量化**

商品详情采用 Caffeine（L1，3 秒 TTL）+ Redis（L2，带逻辑过期）两级缓存。**缓存穿透**用「参数校验 + Redis 布隆过滤器 + 空值缓存」三层防护，其中布隆过滤器不支持删除的特性正好解释了为什么空值缓存不可省略；**缓存击穿**用两套互补机制——热 key 到期走逻辑过期（返回旧数据 + 异步重建，用户零等待），冷 key 不存在走 Redisson 互斥锁 + 双重检查（没抢到锁的请求短暂自旋等缓存回填，而不是直接查库，否则加锁只保护了一个请求）；**缓存雪崩**用物理 TTL 随机抖动打散失效时刻。写入侧遵循 Cache Aside 且**先更新数据库、再删除缓存**，删除动作通过 `@TransactionalEventListener(AFTER_COMMIT)` 推迟到事务提交之后（否则先删缓存再提交会让并发读把旧值回填、且长期无人修正），并叠加 500ms 延迟双删兜住"读请求在删除前取到旧值、在删除后回填"的更窄窗口。本地缓存无法被其他实例失效这一固有缺陷被明确量化：`l1-ttl` 就是多实例部署下的不一致窗口上界。

**6. 工程化：把"我觉得没问题"替换成可观测的事实**

业务埋点覆盖秒杀各分支占比、Lua 耗时分布、**缓存各层命中率**与 MQ 全链路事件，并区分「限流拒绝」与「限流组件故障降级」两类指标。运维接口可即时拉取 Redis 侧库存/在途/已购人数、库存对账结果、待确认投递数。声明式限流通过 AOP + `@RateLimit(rule, dimensions)` 实现，阈值集中在配置中管理；同时实现滑动窗口（ZSET，严格削峰，用于秒杀）与令牌桶（HASH，O(1) 内存、允许突发，用于登录）两种算法，并按"接口的真实成本"分配阈值；限流组件故障时默认 **fail-open 放行 + 告警**，避免把一次局部故障放大成全站不可用。

### 效果验证

- **并发正确性（43 个自动化测试全部通过）：** 800 虚拟线程抢 200 库存，**成功次数恰好 200**、Redis 剩余库存恰好 0、已购集合恰好 200；同一用户 500 并发仅 1 次成功；重复回补 5 次库存被总库存封顶；200 并发打 limit=20 的限流器**恰好放行 20 个**；同一消息消费两次只产生一个订单且库存只扣一次。
- **缓存效果：** 10 万请求压测商品详情，服务端统计 L1 命中率 **99.65%**、端到端观测 **99.9% 命中 L1 / 0.1% 命中 L2 / 数据库 0 次访问**。
- **吞吐：** 单机自压（客户端与服务端同机争抢 CPU）测到 **13,102 QPS**、服务端平均处理 **1.118ms**；因是同机压测，该数字是**下界而非上限**。
- **故障降级：** 在 RabbitMQ **完全不可用**的情况下用 2 万并发请求打秒杀接口，3,801 次走完"扣减→投递失败→补偿"完整路径，最终 5 个活动**全部 `drift = 0`、在途归零、已购集合清空**——零库存泄漏、零超卖；代价是 P95 从毫秒级劣化到 2 秒（broker 重连退避 + 补偿路径开销）。
- **一项被数据纠正的判断：** 首版压测用 Python 脚本，测出 738 QPS / 平均 247ms。但服务端自测平均耗时只有 1.68ms——差值全在客户端。据此改用 Java 21 虚拟线程客户端，同一服务同一接口测到 **13,102 QPS，相差 17.7 倍**。由此固化了一条纪律：**报 QPS 之前必须先证明瓶颈不在压测客户端**。

## 面试官最可能追问的 8 个点（及应对）

| 追问 | 应对要点 |
|---|---|
| "怎么保证不超卖？" | 三级漏斗 + **给出测试证据**（800 并发抢 200，成功数恰好 200）。不要只讲原理 |
| "Redis 和 MySQL 数据不一致怎么办？" | 先说补偿三层防重，再说对账兜底，最后说**在途计数既修正也掩盖故障**这个洞察 |
| "为什么不用分布式锁？" | 往返次数对比 + 锁自身的风险清单（超时/续期/误删）+ "什么时候我会用锁" |
| "MQ 挂了会怎样？" | 直接给故障演练数据：2 万并发、drift 全 0；并主动说代价（P95 劣化到 2 秒） |
| "缓存一致性怎么保证？" | 先更库再删缓存 → AFTER_COMMIT → 延迟双删，**并主动给出不一致窗口上界（3 秒）** |
| "你的 QPS 数字可信吗？" | **主动坦白**这是单机自压、客户端与服务端争抢 CPU，说明为什么它是下界，以及怎么测真实容量 |
| "这个架构有什么问题？" | 主动说：单机 Redis、缓存失效依赖应用层（应接 binlog）、内存台账不如 Outbox 可靠 |
| "如果重做你会改什么？" | 接 Canal 做缓存失效、把秒杀热路径的 Redis 往返再拆一层、补全链路压测与 Trace |
