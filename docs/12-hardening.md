# 12 · 代码评审驱动的加固记录

> 这份文档记录的<b>不是"我要加什么功能"，而是"我在自己的代码里发现了什么错"</b>。
>
> 项目做久之后最危险的错觉是"能跑 = 正确"。下面这 9 个问题都是**测试全绿、演示正常**
> 但逻辑上确实错了的缺陷，全部来自一次针对"生产环境会发生什么"的逐行复查。
>
> 面试价值：能把"我发现并修复了一个不会报错的 bug"讲清楚，比列举十个技术栈有说服力。

---

## 已修复

### 1. 对账修复写完库存，紧接着被预热覆盖 —— `SeckillReconcileService`

**症状**：对账发现漂移后，修复逻辑先 `resetStock(targetStock)`，随后调用
`preheatService.preheat()` 重新预热；而预热写的是 **DB 的 `available_stock`**，
把刚算好的 `targetStock`（= DB 库存 − 在途数）覆盖掉了。

**为什么危险**：存在合法在途消息时，`targetStock < dbAvailable`。
覆盖等于把"还没落库的预留库存"重新放回秒杀入口——**修复动作本身制造了超卖的窗口**。

**修复**：`repair()` 不再调用预热，只清本地快照（`evictLocal`），
库存数值以对账算出的目标值为准。

---

### 2. `drift-tolerance` 配置了但从未生效 —— `SeckillReconcileService`

**症状**：`mall.reconcile.drift-tolerance` 写在配置里、有注释、有默认值，
但代码里判断的是 `drift == 0`，这个配置从头到尾没被读过。

**为什么危险**：活动进行中，Redis 与 DB 之间本来就可能有 1~2 个请求的瞬时抖动。
零容忍会把正常抖动判成故障，触发一次本不该发生的"自动修复"。

**修复**：按 `Math.abs(drift) <= tolerance` 判定一致，容忍范围内的漂移只记录不修复。

---

### 3. 活动状态字段永远停在创建时的值 —— `ActivityStatusSyncJob`（新增）

**症状**：`t_seckill_activity.status` 是 `start_time / end_time` 的派生值，
但全库只有种子数据写过它，**没有任何任务在维护**。

**为什么危险**：活动结束三个月后，`GET /api/seckill/activities?status=1`
仍然能筛出它；运营后台显示"进行中"，用户点进去发现已结束。
这类问题不报错、不告警，只会让运营逐渐不信任数据。

**修复**：新增每 30 秒对齐一次的任务，一条 `UPDATE ... WHERE status <> 新值`
把状态纠正过来；稳态下不产生任何写入。

---

### 4. 抢购结果轮询每次都查数据库 —— `SeckillController`

**症状**：`GET /api/seckill/result/{orderNo}` 每次都 `SELECT ... FROM t_order`。

**为什么危险**：秒杀结束后的轮询是典型的"少量数据、极高频率"访问。
一个等结果的用户每分钟能产生几十次 DB 读——**刚扛过写洪峰的数据库，
会被自己的读流量再打一遍**。而且这个接口之前连限流都没有。

**修复**：
- 订单落库时把订单快照写入 Redis（`seckill:order:{orderNo}`，TTL 5 分钟）；
- 轮询优先读快照，归属校验也在缓存层完成（快照里带 `userId`）；
- 补上按用户的限流规则（10/s），不按 IP——轮询是正常行为，按 IP 会误伤 NAT 后的整栋楼。

---

### 5. 支付重复回调返回失败 —— `OrderService.pay`

**症状**：订单已是 `PAID` 时，第二次支付回调抛 `ORDER_STATUS_CONFLICT`。

**为什么危险**：支付网关对非 2xx **会持续重试**（有的重试 24 小时）。
用户侧表现为"钱扣了，订单还是待支付"。这是支付领域最经典的故障模式。

**修复**：区分两种语义——
- **同向重复**（已支付 → 再支付）：幂等返回成功；
- **反向冲突**（已取消 → 支付）：仍然拒绝。

测试同步改为断言幂等成功，并补了一个"已取消订单不可支付"的用例。

---

### 6. 已购集合可能永不过期 —— `seckill_deduct.lua`

**症状**：预热时对 `seckill:bought:{act:N}` 调 `EXPIRE`，但此时集合往往还不存在。
**Redis 对不存在的 key 设置过期时间直接返回 0**，而后续 `SADD` 创建新 key
也不会继承任何 TTL。

**为什么危险**：集合永久驻留，活动结束、Key 过期后它还在吃内存，
长跑几个月就是一次内存泄漏。

**修复**：把 TTL 放进扣减脚本，`SADD` 之后判断 `TTL < 0` 则补设——
"谁创建谁负责"，与调用顺序解耦。

---

### 7. 任何登录用户都能调用运维接口 —— `AdminInterceptor`（新增）

**症状**：`/api/admin/**` 只校验了登录，没有校验角色。而其中的接口能：
触发对账并**自动修复**（改写 Redis 库存）、清缓存、覆盖预热快照。

**修复**：新增管理员拦截器，按配置白名单（`mall.admin.usernames`）拦截。
演示项目刻意不引入完整 RBAC——三张权限表对没有运营后台的项目是过度设计，
但"任何注册用户都能改库存"是不可接受的。文档里写清了生产该怎么做。

---

### 8. 虚拟线程没开 —— `application.yml`

**症状**：pom 用 Java 21、文档强调虚拟线程，但 `spring.threads.virtual.enabled`
从未配置，Web 层跑的还是 Tomcat 的 500 个平台线程。

**修复**：开启虚拟线程（可用 `VIRTUAL_THREADS=false` 关闭做对照压测）。
注释里同时写明它**不解决**连接池不够用的问题——压测要一起看 Hikari 的 pending。

---

### 9. 只有日志、没有 traceId —— OpenTelemetry 接入

**症状**：跨 MQ 的生产/消费链路在日志里是断开的，出问题只能靠时间戳硬猜。

**修复**：接入 `micrometer-tracing-bridge-otel` + OTLP 导出；
打开 RabbitMQ 的 `observation-enabled`（消息头传递 trace 上下文）；
日志格式加 `%X{traceId:-}`。默认不导出（CI 没有 collector），
docker profile 里指向 compose 中的 Jaeger，采样率压测时设 0。
