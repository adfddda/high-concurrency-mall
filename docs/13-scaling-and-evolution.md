# 13 · 扩容与演进：分库分表、Canal、多级扩容

> **本文的定位**：这是**设计文档，不是实现说明**。文中三件事在代码里都没有实现。
>
> 为什么要把"没做的事"写得这么细：
> 面到"你的系统怎么扩容"这类问题时，"我们以后会分库分表"是最差的答案；
> 而"分片键选 user_id、唯一约束因此仍然成立、按订单号查要广播、迁移分四步"是可讨论的答案。
> **能讲清楚为什么还没做、以及做的时候第一步是什么，比含糊地声称做过更专业。**

---

## 1. 先判断：现在该不该分

分库分表是**用复杂度换容量**的交易。触发它的应该是数据量而不是"听起来高级"：

| 信号 | 当前值 | 触发阈值 | 结论 |
|---|---|---|---|
| 单表行数 | 演示环境 < 1 万 | 2000 万（B+ 树变高、DDL 变慢） | 未触发 |
| 单库写入 TPS | 压测约 1k（含异步落库） | 单实例 3k~5k | 未触发 |
| 单库存储 | < 1 GB | 单实例 2 TB | 未触发 |
| 单活动峰值 QPS | 13k（Redis 承担） | Redis 单分片 8~10 万 | 未触发 |

**按这个表，当前系统不需要分片。** 需要先做的是：读写分离（读多写少时性价比最高）、
订单历史归档（把 90 天前的订单挪到冷表）、慢查询治理。这三件事的成本比"分片"低一个数量级。

## 2. 分库分表设计（未实现）

### 2.1 分片键：`user_id`

理由（按优先级）：

1. **最高频的查询天然带分片键**：`/api/order/list` 按 user_id 查，能精确路由；
2. **`uk_user_activity` 的唯一性自动成立**：同一用户的订单永远落在同一分片，
   分片内的唯一索引 = 全局唯一索引。**这是最容易被忽略、也最关键的一点**——
   如果按 `order_no` 分片，"一人一单"的数据库兜底就废了；
3. 单个用户的订单量有界（不会出现超级分片）。

代价：

- 按订单号查询会**广播到所有分片**（用户打开订单详情时）；
- 按活动统计需要另一条路径（见 2.4）。

### 2.2 表与分片规划

```text
t_order        → 4 库 × 4 表 = 16 片，分片键 user_id
t_order_item   → 与 t_order 同分片键（user_id 冗余一列），保证订单+明细同片、单事务
t_mq_message   → 不分片（按 message_id 全局唯一，是幂等闸门）
t_seckill_*    → 不分片（活动表只有几十行；库存热点靠 Redis 分桶解决，不靠分库）
t_user/t_sku   → 不分片
```

> 明细表冗余 `user_id` 是有意的：为了"订单与明细在同一分片、能在一个本地事务里写"。
> 代价是一列冗余和一次写入校验，换掉的是分布式事务——**非常划算**。

### 2.3 唯一约束清单（分片后逐条核对）

| 约束 | 分片后是否仍然成立 | 原因 |
|---|---|---|
| `uk_order_no` | ✅ | 雪花 ID 全局唯一，不需要数据库保证 |
| `uk_user_activity` | ✅ | 含 user_id，与分片键一致 |
| `uk_message_id` | ✅ | 同一消息只可能对应同一用户，落同一分片 |
| `uk_order_change`(t_stock_flow) | ✅ | 表不分片 |

**这张表就是"能不能分"的检查清单。** 只要有一条含非分片键的全局唯一约束，
就必须先把它挪到独立表（例如限购表 `t_purchase_limit(user_id, activity_id)`）。

### 2.4 两类跨分片查询

| 查询 | 来源 | 处理 |
|---|---|---|
| 按 `order_no` 查 | 订单详情、支付回调 | **广播查询**（16 片并发，P99 可接受）；高频时加 `t_order_route(order_no → user_id)` 路由表 |
| 按 `activity_id` 统计 | 运营后台、对账 | 建**异构索引表** `t_activity_order_index(activity_id, order_no)`，分片键改为 activity_id |
| 分页 `count(*)` | 后台列表 | 各分片求和（ShardingSphere 自动做），**禁用深度 offset 分页**，改 keyset |

### 2.5 迁移路径（不停机）

```text
① 双写：写主库的同时写分片库（新库），用 user_id 路由
② 校验：影子读——按 user_id 从分片库读，与主库结果比对（差异率 < 0.01% 才继续）
③ 切读：订单列表/详情切到分片库，主库只写
④ 切写：停双写，主库转只读（历史数据按需归档）
```

风险控制：

- ①~④ 每一步都能独立回滚（双写期间主库始终是权威）；
- 用 `user_id % 100` 灰度切流，而不是一次全量；
- 切换期间**写路径的幂等键不能变**（order_no / message_id 不变），否则重复消费会失效。

### 2.6 分片后确定会遇到的问题

1. **分布式事务**：跨分片写（例如"扣库存 + 建订单"）不再是一个本地事务。
   缓解：库存与订单按同一分片键路由（都带 user_id），或走"本地消息 + 对账"；
2. **分页**：`LIMIT 100000, 10` 在 16 个分片上各扫 10 万行——必须改 keyset 分页；
3. **聚合统计**：`SUM/COUNT` 由中间件归并，延迟随分片数线性上升 → 报表走 ClickHouse；
4. **DDL**：16 片要改 16 次（ShardingSphere 提供 `REFRESH TABLE METADATA` 与在线 DDL 配合）。

## 3. Canal：把缓存/索引失效从应用层解耦（未实现）

### 3.1 现在的问题

当前缓存失效靠应用内 `ProductChangedEvent` + `AFTER_COMMIT` 删除。它有三个盲区：

1. **绕过应用的写入**（DBA 改数据、其他服务写同一个库）不会触发失效；
2. **多实例**下 L1 本地缓存无法被其它实例失效（只靠 3 秒 TTL 收敛）；
3. ES 索引同步同理，只覆盖经过应用的写。

### 3.2 目标架构

```text
MySQL binlog ──► Canal Server ──► MQ(topic: mall.binlog.product) ──► 消费者
                                                                      ├─ 删 Redis（L2）
                                                                      ├─ 广播删 L1（Pub/Sub）
                                                                      └─ 更新 ES 索引
```

关键设计点：

| 问题 | 处理 |
|---|---|
| **重复消费** | binlog position 作为幂等键；删缓存本身幂等，重复无害 |
| **乱序** | 消费者比较 `update_time`，旧版本事件直接丢弃（宁可不删，也不能用旧值覆盖新值） |
| **延迟** | binlog → MQ 通常 < 100ms；仍保留现有 `AFTER_COMMIT` 删除作为"快路径"，Canal 是"兜底路径" |
| **多实例 L1** | 用 Redis Pub/Sub 广播 `evict:{productId}`，每个实例订阅后清本地 Caffeine |
| **位点丢失** | Canal 侧持久化位点；消费者用"最新事件时间"做补偿扫描 |

### 3.3 与现有实现的关系

**不是替换，是叠加**：

- 应用内事件：快（事务提交后立刻删），覆盖 99% 场景；
- Canal：全（覆盖任何来源的写）+ 多实例一致性；
- 对账式全量重建：兜底（例如每小时把热点商品的缓存按 DB 重建一遍）。

## 4. 扩容顺序（先做便宜的）

| 阶段 | 手段 | 成本 | 收益 | 何时做 |
|---|---|---|---|---|
| 1 | 读写分离 + 从库 | 低 | 读容量 ×N | 读 QPS 到单库 70% |
| 2 | 历史订单归档（90 天外） | 低 | 单表行数下降 | 单表 > 1000 万 |
| 3 | 缓存分层与热点探测 | 低 | DB 压力 ↓ | 已做 |
| 4 | Redis Cluster + 库存分桶 | 中 | 单活动吞吐 ×分片数 | 单活动 > 5 万 QPS |
| 5 | 分库分表 | 高 | 写入容量 ×N | 单库写 > 3k TPS |
| 6 | 单元化（按用户地域路由） | 极高 | 跨机房容灾 | 多地域业务 |

> 顺序的原则：**先做不改数据模型的**。分库分表放最后，因为它一旦做了就很难回头。

## 5. 验收标准（如果真要做）

| 项 | 验收方式 |
|---|---|
| 分片正确性 | 新增测试：同一用户订单始终落在同一分片；`uk_user_activity` 仍能拦住重复购买 |
| 双写一致性 | 影子读比对，差异率 < 0.01% 且持续 24h |
| 广播查询性能 | 按 order_no 查询 P99 < 50ms（16 片并发） |
| Canal 延迟 | binlog 产生到缓存失效 P99 < 500ms |
| 回滚 | 每一步都能在 5 分钟内切回主库 |
