# 高并发商城项目 — 面试讲解指南

> 本文档整理面试时讲解本项目的完整话术、架构图、模块亮点、高频问题及回答要点。
> 适用场景：Java 后端开发面试，项目介绍环节。

---

## 一、项目自我介绍（1分钟 / 3分钟版本）

### 1.1 一句话版本

> 这是一个基于 Spring Boot + Redis + RabbitMQ 的高并发秒杀商城项目，核心解决秒杀场景下的超卖、缓存击穿、消息可靠性三大问题，通过 Redis Lua 原子扣库存、多级缓存、MQ 异步下单 + 三层补偿防重等设计，支撑万级 QPS 的秒杀场景。

### 1.2 三分钟版本

> 这个项目是一个高并发商城，核心模块包括用户认证、商品多级缓存、分布式限流、秒杀全链路、订单超时关单。我主要负责了秒杀链路和 MQ 可靠性的设计。
>
> 技术栈用的是 Spring Boot + MyBatis-Plus + Redis + Caffeine + RabbitMQ + MySQL。
>
> 项目最大的亮点有三个：
> 1. **秒杀不超卖**：用 Redis Lua 脚本在一个原子操作内完成库存校验、扣减、一人一单判断，避免了分布式锁的性能瓶颈；同时用「在途计数」做 Redis 和 DB 的对账。
> 2. **缓存高可用**：Caffeine 本地缓存 + Redis 分布式缓存的多级架构，逻辑过期 + 异步加锁重建解决缓存击穿，布隆过滤器防穿透，延迟双删保证缓存一致性。
> 3. **MQ 不丢消息**：发送端 Confirm/Return 双回调 + 超时扫描三重保障，消费端手动 ACK 区分五种结果，延迟重试队列避免零间隔自旋，补偿服务三层防重（查订单 + SETNX 守卫 + Lua 总库存封顶），死信消费者先查订单再补偿防止超卖。
>
> 另外还有分布式限流（令牌桶 + 滑动窗口两种算法，Redis Lua 实现）、线程池隔离（4个线程池各司其职）、订单超时关单（延迟队列 + 条件更新）等设计。

### 2.2 核心设计原则

| 原则 | 体现 |
|------|------|
| **宁可少卖，绝不超卖** | Lua 原子扣减、补偿三层防重、死信先查订单 |
| **数据库是权威，缓存是可重建的投影** | 先提交 DB 事务再回补 Redis，对账任务兜底 |
| **缓存用删除不用更新** | Cache Aside 模式，删除幂等 |
| **线程池隔离** | 4个线程池各司其职，防止一个功能拖垮全局 |
| **消息至少一次 + 消费幂等** | 手动 ACK + 唯一键防重复消费 |

## 三、核心模块逐个讲解（面试话术）

### 3.1 分布式限流模块

**面试官可能问：你们怎么做限流的？**

> 我们用了两种限流算法，根据场景选择：
>
> **登录接口用令牌桶**：60秒最多10次，rate=0.5个/秒，capacity=10。令牌桶允许突发——比如用户一分钟没操作，攒了10个令牌，可以一次性发10个请求。用 Redis Hash 存 `tokens` 和 `lastRefillTime` 两个字段，每次请求时根据时间差计算应该补充多少令牌，Lua 脚本原子完成。
>
> **商品详情和秒杀接口用滑动窗口**：1秒内最多50次（商品详情）/ 5次（秒杀下单）。用 Redis ZSET 实现，score 是时间戳，member 是「时间戳+UUID」保证唯一（防止同一毫秒的请求被覆盖），每次请求时移除窗口外的元素，统计窗口内数量。
>
> 两种算法都通过 Redis Lua 脚本保证原子性，一次 RTT 完成判定。限流组件是 fail-open 的——Redis 故障时降级放行，因为限流是保护手段，不能因为 Redis 挂了导致服务不可用。
>
> 维度上支持 IP、用户、接口等多种维度，通过 AOP 注解拦截，规则配置化。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| 令牌桶和滑动窗口区别？ | 令牌桶允许突发（桶满了可以一次性用完），滑动窗口是硬限制（窗口内绝对不能超）。登录用令牌桶因为用户可能集中操作，秒杀用滑动窗口因为要严格限制抢购频率 |
| 为什么用 Lua？ | 读+判断+写需要原子性，Lua 在 Redis 服务端执行，一次 RTT，避免竞态 |
| ZSET 的 member 为什么用 UUID？ | ZSET 的 member 必须唯一，同一毫秒内多个请求如果用固定值会被覆盖，计数偏低 |

### 3.2 认证模块

**面试官可能问：登录认证怎么做的？登出怎么处理？**

> 用 JWT + Redis 黑名单的方案。
>
> **登录**：用户名密码登录，BCrypt 加盐哈希校验密码，用户不存在和密码错误返回同一个错误码防止枚举攻击。登录成功生成 JWT，包含 userId、jti（令牌唯一标识）、过期时间。
>
> **鉴权**：拦截器解析 Token，校验签名和过期时间，查 Redis 黑名单判断是否已登出，通过后把用户信息存入 ThreadLocal（UserContext），请求结束后在 afterCompletion 里清理，防止 Tomcat 线程池复用导致越权。
>
> **登出**：解析 Token 拿到 jti，把 jti 写入 Redis 黑名单，TTL 等于 Token 剩余有效期。如果请求没带 Token，从 UserContext 兜底拿 jti。黑名单按 jti 而不是 userId 拉黑，这样只拉黑当前设备的 Token，不影响其他设备登录。
>
> **注册**：不做「先查用户名是否存在再插入」，直接 INSERT 靠数据库唯一索引 uk_username 兜底，因为先查再插有竞态窗口。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| 为什么用 jti 不用 userId 做黑名单？ | userId 拉黑会把该用户所有设备都踢下线，jti 只拉黑当前 Token |
| ThreadLocal 为什么要清理？ | Tomcat 工作线程是池化复用的，不清理的话下一个请求会读到上一个用户的身份，是越权漏洞 |
| JWT 无状态，怎么实现主动登出？ | 用 Redis 黑名单，牺牲一点无状态性换取主动失效能力 |

### 3.3 多级缓存模块

**面试官可能问：缓存怎么设计的？缓存击穿/穿透/雪崩怎么解决？**

> 用 Caffeine 本地缓存（L1）+ Redis 分布式缓存（L2）的多级架构。
>
> **L1 Caffeine**：进程内，纳秒级访问，3秒 TTL，不共享，用来挡掉大部分热点读请求。
>
> **L2 Redis**：分布式共享，毫秒级，用逻辑过期——key 不物理删除，过期时间存在 value 里，过期后立即返回旧数据，同时异步加锁重建缓存。这样即使缓存过期，用户也不会被阻塞。
>
> **缓存击穿**：用互斥锁回源——缓存未命中时尝试抢 Redis 锁，抢到的线程查库重建缓存，没抢到的线程自旋等待缓存；等待超时后降级直查 DB 但**不回填**（因为无锁线程写缓存可能用旧数据覆盖持锁者的新数据）。
>
> **缓存穿透**：用 Redis 布隆过滤器，启动时全量加载商品 ID，查询时先过布隆过滤器，不存在直接返回；同时对不存在的商品缓存空值（短 TTL），防止布隆过滤器误判流量和商品删除后的重复查询。
>
> **缓存雪崩**：Redis key 的物理 TTL 加随机抖动，避免大量 key 同时过期；多级缓存本身也有缓冲作用。
>
> **缓存一致性**：用 Cache Aside 模式——写库后删缓存（不是更新缓存，删除是幂等的）。为了堵「事务提交前查到旧值、提交后才写回」的竞态窗口，用延迟双删：AFTER_COMMIT 第一次删，500ms 后第二次删（用单线程调度器执行）。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| 为什么逻辑过期不直接删 key？ | 物理删除后大量请求同时回源会打挂 DB，逻辑过期返回旧数据+异步重建，用户无感知 |
| 为什么没抢到锁的线程不回填缓存？ | 无锁线程查到的可能是旧数据，回填会覆盖持锁者刚写入的新数据 |
| 布隆过滤器的缺点？ | 有误判率（可能把不存在的判断为存在），不支持删除，所以需要空值缓存兜底 |
| 延迟双删为什么是500ms？ | 经验值，覆盖「事务提交前读旧值→事务提交→写回缓存」的时间窗口 |
| 为什么删缓存不是更新缓存？ | 更新缓存可能写旧值覆盖新值（并发写），删除是幂等的，下次读时自动回源 |

### 3.4 秒杀模块（重点）

**面试官可能问：秒杀怎么防止超卖？整个流程讲一下。**

> 秒杀全链路分6步：
>
> **第1步：活动校验**：先查 Caffeine 里的活动快照（5秒 TTL），命中直接用，未命中查 Redis，再没有查 MySQL。返回服务器时间防止前端改时间作弊。
>
> **第2步：本地售罄标记**：Caffeine 里存一个售罄标记（10秒 TTL），如果标记为售罄直接拒绝，不碰 Redis，挡掉无效流量。
>
> **第3步：生成订单号和消息ID**：订单号用雪花ID（"SO"+IdWorker.getIdStr()），消息ID用 UUID 去横杠。
>
> **第4步：Redis Lua 原子扣库存**：这是核心。一个 Lua 脚本内完成：①校验库存是否充足 ②扣减库存 ③校验一人一单（查已购集合）④加入已购集合 ⑤在途计数+1。返回4种状态码（0成功/1售罄/2重复/3未预热）。不用分布式锁是因为锁的粒度大、性能差，Lua 是 Redis 服务端原子执行，性能更好。
>
> **第5步：发 MQ 异步下单**：扣库存成功后，写「排队中」结果到 Redis，发消息到 RabbitMQ，立即返回「已受理」给用户。用户通过轮询接口查结果。
>
> **第6步：消费端创建订单**：消费者手动 ACK，创建订单（同事务写消息台账保证幂等），更新结果为成功。
>
> **活动预热**：定时任务每分钟扫描即将开始的活动，把库存、活动快照、已购集合 TTL 预热到 Redis。预热用 availableStock 而不是 totalStock，防止重新预热超卖。预热后清本地售罄标记和活动快照缓存。
>
> **在途计数**：记录「Redis已扣但订单未落库」的数量，用于对账，公式是 Redis库存 + 已落库订单 + 在途 = 总库存。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| 为什么不用分布式锁？ | 锁粒度大（锁整个活动），并发性能差；Lua 是 Redis 服务端原子执行，不需要锁，性能更好 |
| 一人一单怎么实现？ | Redis Set 存已购 userId，Lua 里 SISMEMBER 判断，SADD 加入，和扣库存同一个原子操作 |
| 为什么用异步下单不直接创建订单？ | 秒杀是写密集场景，同步创建订单会占用 Redis 连接和线程太久，异步下单让接口快速返回，消费端慢慢处理 |
| 本地售罄标记为什么有用？ | 售罄后大部分请求是无效的，用 Caffeine 本地标记直接挡掉，不碰 Redis，减轻 Redis 压力 |
| 预热为什么用 availableStock？ | 如果用 totalStock，活动进行中重新预热会把已扣的库存加回来，导致超卖 |
| 在途计数有什么用？ | 对账，发现 Redis库存 + 已落库订单 + 在途 ≠ 总库存时说明有异常，需要修复 |

### 3.5 MQ 可靠性模块（重点）

**面试官可能问：怎么保证消息不丢？消费失败怎么处理？**

> 从发送端、Broker、消费端三层保证：
>
> **发送端三重保障：**
> 1. **发送异常**：catch 里立刻补偿
> 2. **Confirm/Return 双回调**：Confirm 告诉生产者 broker 收没收消息（ack=false 就补偿），Return 告诉生产者消息路由没路由到队列（触发了就补偿）。用 Caffeine 存 messageId→业务消息的映射，回调时找回上下文。
> 3. **超时扫描**：broker 静默失联时回调永远不来，定时任务每2秒扫描 Caffeine 里待确认的消息，超过5秒没收到 Confirm 就补偿。
>
> **消费端五种结果处理（手动 ACK）：**
> 1. 成功 → ACK
> 2. 幂等命中（消息已消费过）→ ACK
> 3. 唯一键冲突（订单已存在）→ 补偿后 ACK
> 4. 不可重试失败 → 补偿后 NACK(requeue=false) 进死信
> 5. 可重试失败 → republish 到延迟重试队列（5秒 TTL，DLX 回主队列），ACK 原消息；重试3次耗尽后进死信
>
> **延迟重试队列**：没有消费者，消息躺5秒后 TTL 过期通过 DLX 回到主队列，避免 `requeue=true` 的零间隔自旋。
>
> **死信消费者**：先查数据库订单是否存在，存在就不补偿（可能 ACK 时 channel 断了，业务其实成功了），不存在才补偿。
>
> **补偿三层防重**：因为同一条消息可能从5个入口触发补偿，所以①先查订单是否存在 ②Redis SETNX 补偿守卫（24小时）③Lua 回补时总库存封顶。
>
> **消费幂等**：消息台账用数据库唯一键 uk_message_id，消费记录和订单创建在同一个事务里。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| Confirm 和 Return 区别？ | Confirm 是 broker 收没收消息，Return 是消息到了交换机但路由不到队列；ack=true 不代表路由成功，所以两个都要开 |
| 为什么用延迟队列不用 requeue=true？ | requeue=true 会零间隔立刻重投，下游故障时只会更糟；延迟队列给下游5秒恢复时间 |
| 死信消费者为什么先查订单？ | 消息进死信不代表业务失败，可能订单已创建只是 ACK 时断了，无脑回补会超卖 |
| 补偿为什么要三层防重？ | 发送异常、Confirm nack、Return、超时、消费失败5个入口都可能触发同一条消息的补偿，不设防会重复回补超卖 |
| 消费幂等为什么用唯一键不用先查再插？ | 先查再插有竞态窗口，唯一键是数据库索引层面保证互斥 |
| 消息台账为什么和订单同事务？ | 分开的话业务回滚后消息记录还在，重试时被误判为已消费直接 ACK，消息被永久丢弃 |

### 3.6 订单超时关单模块

**面试官可能问：订单超时未支付怎么处理？**

> 用 RabbitMQ 延迟队列实现。
>
> 订单创建成功后，发一条消息到 `order.delay.queue`，这个队列没有消费者，配置了队列级 TTL（30分钟）和 DLX（指向关单交换机）。消息躺30分钟后 TTL 过期，通过 DLX 自动转发到 `order.close.queue`，关单消费者消费。
>
> 关单用**条件更新**：`UPDATE t_order SET status=2 WHERE order_no=? AND status=0`，通过影响行数判断：
> - 影响1行 → 订单还是待支付，关单成功，回补库存
> - 影响0行 → 订单已支付或已取消，什么都不做
>
> 回补 Redis 库存放在**数据库事务提交之后**，因为 Redis 不参与事务，放在事务内如果后续回滚 Redis 已经加回去了会超卖。先提交 DB 再回补 Redis，最坏情况是 Redis 没来得及加回去，对账任务会修回来。
>
> 关单时 `releaseQualification=false`（一人一单资格不回收），`decInflight=false`（在途计数下单成功时就归还了）。
>
> 还有兜底扫描任务 `OrderTimeoutFallbackJob`，定期扫描已过期但仍未支付的订单，防止消息丢失。

**可能的追问：**

| 问题 | 回答要点 |
|------|---------|
| 为什么用延迟队列不用定时任务扫表？ | 延迟队列每条消息独立计时，精确到秒，不扫表；定时任务扫表有延迟且订单多了性能差 |
| 为什么条件更新不用先查再改？ | 支付和关单是并发竞争的，先查再改有竞态，条件更新是数据库原子操作 |
| 回补 Redis 为什么在事务提交后？ | Redis 不参与事务，放事务内回滚时 Redis 无法撤销会超卖 |
| 为什么资格不回收？ | 用户已经抢到了资格只是没付钱，回收了用户重新抢会在 Redis 通过但 DB 撞唯一键，体验差 |

### 3.7 线程池隔离

**面试官可能问：为什么配置多个线程池？**

> 配置了4个线程池/调度器，各司其职：
>
> | 池子 | 线程数 | 用途 |
> |------|--------|------|
> | cacheRebuildExecutor | 可配置 | 缓存逻辑过期后异步重建 |
> | taskScheduler | 4 | 所有 @Scheduled 定时任务 |
> | cacheDoubleDeleteScheduler | 1 | 缓存延迟双删（500ms后第二次删） |
> | seckillCompensateExecutor | 4核心/8最大 | 秒杀失败时回补库存 |
>
> 分开的目的是**线程池隔离**——如果缓存重建任务积压，不会影响定时任务的执行；如果秒杀补偿任务阻塞，不会影响缓存双删。防止一个功能的线程积压把其他功能也拖垮。
>
> 缓存重建用 CallerRunsPolicy（调用者自己执行），作为背压机制，线程池满了就让调用线程自己干活，防止任务无限堆积。

### 3.8 MyBatis-Plus 配置

**面试官可能问：MyBatis-Plus 做了哪些配置？**

> 配置了三个拦截器，都挂在 MybatisPlusInterceptor 总容器下：
>
> 1. **分页拦截器**：maxLimit=500 防止 pageSize=1000000 打挂 DB；overflow=false 防止翻到最后一页还在无限翻的爬虫行为。
> 2. **乐观锁拦截器**：实体类带 @Version 字段的更新自动拼 version 条件+自增，防并发覆盖。
> 3. **BlockAttackInnerInterceptor**：拦截没有 WHERE 条件的 UPDATE/DELETE，防止手抖全表操作，开发阶段直接报错。
>
> 注意分页拦截器只拦截分页查询，非分页 SQL 不受影响。

## 四、项目亮点总结（面试结尾用）

> 这个项目我觉得最有价值的几个设计：
>
> 1. **Redis Lua 原子扣减**：不用分布式锁就解决了超卖问题，性能远高于锁方案
> 2. **MQ 全链路可靠性**：发送端三重保障 + 消费端五种结果 + 延迟重试 + 三层防重补偿，消息基本不丢、不重复
> 3. **多级缓存 + 逻辑过期**：缓存过期时用户无感知，异步重建不阻塞请求
> 4. **死信消费者先查订单再补偿**：这个细节很多人会忽略，直接回补会超卖
> 5. **在途计数 + 对账**：Redis 和 DB 最终一致性的兜底机制
> 6. **线程池隔离**：防止一个功能拖垮全局

## 五、面试常见问题速查表

| 问题 | 核心答案关键词 |
|------|--------------|
| 怎么防超卖？ | Redis Lua 原子扣减 + 一人一单 Set + 补偿三层防重 + 死信先查订单 |
| 缓存击穿怎么解决？ | 互斥锁回源 + 逻辑过期异步重建 + 无锁线程不回填 |
| 缓存穿透怎么解决？ | 布隆过滤器 + 空值缓存 |
| 缓存雪崩怎么解决？ | TTL 随机抖动 + 多级缓存 |
| 缓存一致性怎么保证？ | Cache Aside 删缓存 + 延迟双删 + 先提交DB再回补Redis |
| MQ 消息不丢怎么保证？ | 发送端 Confirm/Return/超时三重 + 消费端手动ACK + 持久化 |
| MQ 重复消费怎么解决？ | 消息台账唯一键 + 消费记录与订单同事务 |
| 秒杀为什么用 MQ 异步下单？ | 接口快速返回，削峰填谷，消费端慢慢处理 |
| 令牌桶和滑动窗口区别？ | 令牌桶允许突发，滑动窗口是硬限制 |
| 为什么用 Caffeine？ | 本地缓存纳秒级，挡热点读，减轻 Redis 压力 |
| 布隆过滤器缺点？ | 有误判、不支持删除，需要空值缓存兜底 |
| 延迟双删为什么500ms？ | 覆盖事务提交前读旧值→提交→写回的时间窗口 |
| 订单超时怎么实现？ | 延迟队列 TTL+DLX + 条件更新关单 |
| 为什么回补Redis在事务提交后？ | Redis不参与事务，放事务内回滚会超卖 |
| ThreadLocal为什么要清理？ | Tomcat线程池复用，不清理会越权 |
| 为什么jti做黑名单不用userId？ | jti只拉黑当前Token，不影响其他设备 |

## 六、项目中可能被挑战的点（提前准备）

| 挑战点 | 应对思路 |
|--------|---------|
| 秒杀用 Redis 扣库存，Redis 挂了怎么办？ | 限流组件 fail-open 降级；Redis 高可用部署（哨兵/集群）；对账任务兜底 |
| MQ 消费端创建订单失败，补偿了但用户已经看到排队中怎么办？ | 结果轮询接口会查到 FAILED 状态，前端提示抢购失败，用户可以重新抢购 |
| 延迟队列是队列级 TTL，所有消息过期时间一样怎么办？ | 本项目订单超时时间统一（30分钟），够用；如果需要不同超时时间可以用消息级 TTL 或延迟队列插件 |
| 布隆过滤器有误判，不存在的商品可能被判断为存在 | 误判后会查 Redis/DB，DB 查不到返回空，空值缓存兜底，不会有问题 |
| Caffeine 本地缓存多实例数据不一致 | Caffeine TTL 很短（3-5秒），且只用于读缓存，写操作走 Redis，不一致窗口很小可接受 |
| 对账任务多久跑一次？ | 可配置，一般每分钟或每5分钟，根据业务容忍度调整 |
