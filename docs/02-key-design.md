# 02 · 关键设计决策与取舍

> 面试里真正拉开差距的不是"我用了什么"，而是**"我为什么不用另一个"**。
> 本文把项目里每一个非平凡的技术选择摊开：备选方案是什么、各自的代价是什么、我为什么选了这个、**什么情况下应该换回去**。

---

## 决策 1：秒杀扣减用 Lua，不用分布式锁

| 方案 | 每次抢购的网络往返 | 主要风险 |
|---|---|---|
| **Redis Lua（选用）** | 1 次 EVAL | 脚本要保证幂等、key 必须同槽 |
| Redisson 分布式锁 | 3 次（lock + 业务 + unlock） | 锁超时、看门狗续期、误删他人锁、锁等待堆积 |
| `SETNX` 手写锁 | 3 次 | 上面全部 + 锁不可重入 + 释放非原子 |
| 数据库悲观锁 `SELECT FOR UPDATE` | 1 次事务 + 行锁等待 | 高并发下行锁排队，吞吐量断崖式下跌 |

**为什么选 Lua**：`查库存 → 判断 → 扣库存 → 标记用户` 这四步必须不可分割。
Lua 脚本在 Redis 内部整体串行执行且不会被其它命令插入，天然原子，**不需要锁**。
省下的两次往返在秒杀入口就是 2~3 倍的吞吐差异。

**代价（要主动说）**：
1. 脚本里的所有 key 必须同槽（见决策 4）；
2. 脚本不能写太复杂，**Redis 是单线程的，一个慢脚本会阻塞整个实例**。所以脚本里只做 O(1) 操作，绝不遍历大集合；
3. 调试困难，出问题只能靠日志和 `redis-cli --eval` 复现。

**什么时候该换回锁**：当临界区里包含**多个 Redis 之外的资源**时（比如要同时改 Redis 和调用另一个服务），
Lua 就无能为力了，此时分布式锁才是对的工具。

## 决策 2：Redis 扣减 + MQ 异步落库，而不是同步落库

```
同步落库：  请求 → 扣 Redis → 扣 MySQL → 建订单 → 返回     RT ≈ 5~20ms，DB QPS 就是系统上限
异步落库：  请求 → 扣 Redis → 发 MQ → 返回                 RT ≈ 1~2ms，DB 压力被 MQ 削平
（选用）
```

**收益**：秒杀接口的 RT 与数据库负载**完全解耦**。数据库慢十倍，秒杀接口照样是 1ms。
MQ 充当蓄水池，把瞬时 5 万 QPS 变成数据库能承受的 2000 QPS 持续写入。

**代价——这是必须坦白说的部分**：

| 代价 | 具体表现 | 本项目的应对 |
|---|---|---|
| 用户拿不到最终结果 | 只能返回"排队中" | 结果缓存 + 前端轮询 |
| 引入分布式一致性 | Redis 扣了但订单没落库 | 补偿（三层防重）+ 对账任务 |
| 复杂度显著上升 | 补偿、幂等、死信、对账四套机制 | 全部收敛到 `SeckillCompensationService` / `SeckillReconcileService` |
| 需要额外中间件 | RabbitMQ 的运维成本 | — |

**关键判断：这套架构只适用于"瞬时并发极高、可接受最终一致"的场景。**
普通下单流程同步落库就对了——为了"高并发"把简单流程改复杂，是典型的过度设计。

## 决策 3：权威库存在 MySQL，不在 Redis

很多人会问："既然 Redis 里已经有库存了，为什么还要在数据库扣一次？"

**因为 Redis 的库存是可丢失的投影。**

| | MySQL | Redis |
|---|---|---|
| 持久化 | WAL + 事务，可靠 | RDB/AOF，主从切换可能丢数据 |
| 约束 | 唯一索引 / CHECK / 外键 | 无 |
| 并发正确性 | 行锁 + MVCC | 单线程原子命令 |
| 可回溯 | binlog 可审计 | 无 |

**Redis 的角色是"准入闸门"**——它把 99.9% 必然失败的请求挡在数据库之外；**真正的超卖防线在 `UPDATE ... WHERE available_stock >= 1`**。
即使 Redis 被清空、被误改、主从切换丢数据，数据库这层依然不会让库存变成负数。

**推论**：任何冲突都以数据库为准，Redis 对齐过去（`SeckillReconcileService` 的修复方向）。
反过来做会把已经发生的错误固化进权威数据源。

## 决策 4：Hash Tag —— 让集群可用性在单机环境就能被验证

**问题**：Lua 脚本一次操作 3 个 key，集群模式下必须同槽。

**解法**：`RedisKeys.activityTag(activityId)` 统一生成 `{act:2001}`，三个 key 都带上它。
大括号内**保留 `act:` 前缀**而不是裸的 `{2001}`——不同业务域的数字 ID 容易撞车（活动 2001 vs 商品 2001），
加前缀能避免"两个无关的 key 被强行塞进同一个槽"造成数据倾斜。

**真正的难点不是写法，而是验证**：
单机 Redis **永远不会报 CROSSSLOT**，所以这个错误必然在"开发全绿、上线全崩"时才发现。

**本项目的做法**：
1. 自己实现 `RedisClusterSlot`（CRC16-XMODEM，与 Redis 源码同变体）；
2. 单元测试断言 `crc16("123456789") == 0x31C3`（国际标准校验值）与 `slot("foo") == 12182`（Redis 文档示例），
   确保算的是**同一个变体**——用错变体时"同槽判断"依然自洽，但落到的槽和集群实际分配对不上，问题极难定位；
3. 单元测试断言三个 key 同槽；
4. `SeckillStockService` 启动时自检，不同槽直接启动失败。

## 决策 5：一人一单 —— Redis Set 只是闸门，硬约束在数据库

| 方案 | 优点 | 缺点 |
|---|---|---|
| 纯 Redis Set | 快、无 DB 压力 | 主从切换丢数据 / 缓存被清 / 补偿路径误删 → 挡不住 |
| 纯 DB 唯一索引 | 绝对可靠 | 每个重复请求都要打一次 DB，秒杀场景不可接受 |
| **两层（选用）** | Redis 挡掉 99.9%，DB 兜底 | 需要处理"DB 拒绝后的 Redis 补偿" |

```sql
UNIQUE KEY uk_user_activity (user_id, activity_id)
```

**DB 命中唯一键时如何处理**：这不是"错误"，而是**必须告警的一致性缺口信号**。
处理方式是：回补这条消息对应的 Redis 库存 → ACK → 打指标 → 记 ERROR 日志。
**绝不能重试**——唯一键冲突重试一万次结果都一样，只会把队列堵住（毒丸消息）。

**一个刻意的产品决策**：订单超时被取消时，**库存放回去给别人抢，但不回收该用户的购买资格**。
因为 `uk_user_activity` 依然存在，回收资格只会让用户在 Redis 通过、在 DB 撞唯一键，
产生大量无意义的补偿。一人一单是硬规则，抢到过就不能再抢。

## 决策 6：投递可靠性 —— 内存台账 vs 本地消息表（Outbox）

| | 内存台账 + 超时补偿 + 对账（选用） | 本地消息表（Outbox） |
|---|---|---|
| 热路径 DB 写入 | **0 次** | 1 次 INSERT |
| 进程崩溃 | 丢失上下文，靠对账修复 | 消息不丢，可重投 |
| 实现复杂度 | 中（需要超时扫描 + 对账） | 低（事务保证） |
| 适用场景 | **秒杀这种"热路径绝不能碰 DB"的入口** | 订单状态变更这类"量不大但绝不能丢"的场景 |

**为什么秒杀入口选内存台账**：秒杀接口能扛住高并发，**正是因为把数据库操作全部异步化了**。
为了"可靠"再塞一次 INSERT 进去，等于自毁前提——每一次抢购都要写一次数据库，那 MQ 削峰的意义何在？

**代价用对账来还**：`SeckillReconcileService` 用"在途计数泄漏探测"（见决策 10）修复进程崩溃造成的库存漂移。
本质上是用**最终一致**换**热路径的极致性能**。

**顺带一个真实的坑（可以主动提，很加分）**：
Spring AMQP 的 `CachingConnectionFactory` 会在内存里保存待确认的 `CorrelationData`。
如果 broker 长时间不可达、confirm 一直不来，这个 Map 会**持续增长直到 OOM**。
缓解：本项目用有界 + 有 TTL 的 Caffeine 自己管理上下文，并定时扫描清理超时条目；
生产上还必须对这个 Map 的大小做监控告警。

## 决策 7：消费重试用「延迟队列」，不用 `basicNack(requeue=true)`

```java
// ❌ 立刻重投：失败原因是下游瞬时故障时，等于零间隔自旋
channel.basicNack(tag, false, true);

// ✅ 投递到 TTL=5s 的延迟队列，DLX 再路由回来
messageSender.republish(message, exchange, retryRoutingKey, retryCount + 1);
channel.basicAck(tag, false);
```

`requeue=true` 会把消息**立刻**重新投回队首。如果失败原因是"数据库连接池满了"，
立刻重投只会让数据库更没机会恢复，同时把日志和 CPU 全部打满。

**延迟队列的代价**：
- 需要额外一个队列（+ TTL + DLX 配置）；
- 用**队列级 TTL**，同一队列内所有消息过期时间必须一致。
  如果将来要支持"不同订单不同超时"，消息级 TTL 会造成**队头阻塞**，必须换成延迟插件或按档位拆队列。

## 决策 8：不可重试的失败必须被识别出来

把所有失败都当成"可重试"会产生**毒丸消息**：一条永远失败的消息反复占用消费者、拖慢整个队列。

本项目把失败明确分成四类，每类走不同路径：

| 异常 | 含义 | 处理 |
|---|---|---|
| `DuplicateMessageException` | 消息已经成功处理过 | **ACK**（这是正常现象，不是错误） |
| `DuplicateOrderException` | 用户已有订单，Redis 判定被绕过 | 补偿 Redis → **ACK** + 告警 |
| `NonRetryableMessageException` | DB 库存不足 / 活动不存在等 | 补偿 → **nack(requeue=false) → 死信**（需要人看） |
| 其它 `Exception` | 瞬时故障（连接抖动、超时） | 延迟重试，3 次后进死信 |

## 决策 9：补偿的三层防重

库存补偿是整个系统里**最容易出错**的一段：重复执行 → 超卖，漏执行 → 少卖。

```
第一层：先确认订单确实不存在
        broker 已经路由给消费者、订单已创建，但 Confirm 帧丢失/超时
        → 若无条件回补，结果就是"订单在、库存也还回去了" = 超卖

第二层：SETNX 一次性守卫  seckill:compensate:guard:{messageId}
        发送异常 / Confirm nack / Return 回调 / 超时扫描 / 死信消费，
        五个入口都可能触发补偿

第三层：Lua 里用 total_stock 封顶
        即使前两层都被绕过，库存也不会超过总库存
        —— 把错误限制在"少卖"而不是"超卖"
```

> **宁可少卖，绝不超卖。**
> 少卖只是收入损失，超卖是履约事故 + 品牌事故 + 资损。两者的处理优先级完全不同。

## 决策 10：在途计数既是修正项，也是泄漏探测器

**不变式**：
```
稳态（无在途）：  Redis 库存 == DB available_stock
有在途请求：      Redis 库存 == DB available_stock - 在途数
```

**但它会掩盖故障**：进程在"Redis 已扣减、消息还没确认"时崩溃，
Redis 库存永久少 1，在途计数永久多 1，两者相减正好抵消，`drift` 恒为 0，**单纯比对库存根本发现不了**。

**破局点**：在途是**瞬态量**。正常业务下从扣减到落库只有几十毫秒，
每 5 分钟采样一次几乎不可能采到 `inflight > 0`。
所以**连续多次采样都看到 `inflight > 0`，就等价于发现了泄漏** → 强制对齐到 DB 库存并把在途清零。

**为什么默认只告警、不自动修**：
自动修复的前提是"对账逻辑本身是对的"。对账逻辑一旦有 bug，自动修复会把数据错误放大成持续的数据破坏。
生产建议先只告警跑一段时间，确认 `drift` 恒为 0 后再开 `auto-repair`。

## 决策 11：缓存一致性 —— 为什么是"先更库、再删缓存 + AFTER_COMMIT"

### 为什么删缓存而不是更新缓存

更新缓存在并发下会写入不一致数据：两个写请求的 **DB 提交顺序**与**缓存写入顺序**可能相反，最终缓存里留下旧值。
删除是幂等的——删两次和删一次效果一样。

### 为什么先更库再删

反过来（先删缓存再更库）有一个致命窗口：

```
T1: 删除缓存
T2: 读请求 → 缓存 miss → 查 DB（T1 未提交，读到旧值）
T2: 把旧值写回缓存          ← 关键
T1: 提交事务（DB 变成新值）
结果：DB 新值、缓存旧值，而且在 TTL 到期前没有任何机制会修正它
```

### 为什么必须 `AFTER_COMMIT`

即使改成"先更库再删"，如果在**事务提交前**删缓存，仍会重演上面那段时序。
`@TransactionalEventListener(phase = AFTER_COMMIT)` 保证删除动作发生在数据**真正可见之后**。

> ⚠️ 注意 `fallbackExecution` 默认是 `false`：没有事务上下文时事件会被**静默丢弃**，
> 表现为"改了数据但缓存一直不更新"且没有任何报错。本项目显式设为 `true`。

### 为什么还要延迟双删

即使 AFTER_COMMIT 之后才删，仍有一个更窄的窗口：

```
T2: 读请求 → 缓存 miss → 查 DB 拿到【旧值】（T1 还没提交）
T1: 提交事务
T1: AFTER_COMMIT 删缓存
T2: 把刚才读到的旧值写回缓存    ← 删除发生在回填【之前】，删了个寂寞
```

对策：删除之后再过 500ms **再删一次**，清掉窗口内被回填的脏数据。

### 更强一致性的做法（本项目未实现，但要知道）

订阅 MySQL binlog（Canal / Debezium），按 binlog 顺序消费并删缓存。
好处是**连"应用层忘了删缓存"的漏网都能覆盖**（比如有人直接连库改数据）。
代价是引入额外中间件和一条需要长期维护的链路。

### L1 本地缓存的一致性代价（必须坦白）

本地缓存**无法被其它实例删除**，所以 `l1-ttl` 就是**多实例部署下的不一致窗口上界**。
本项目设 3 秒：商品详情能容忍 3 秒延迟，换来的是 Redis 读 QPS 降一个数量级。
如果不能容忍，就只能砍掉 L1，或者引入 Redis Pub/Sub 广播失效消息。

## 决策 12：防击穿 —— 逻辑过期与互斥锁是互补的

| | 逻辑过期 | 互斥锁 |
|---|---|---|
| 适用 | **热 key 到期**（缓存里有旧数据） | **冷 key 不存在**（首次访问 / 被淘汰 / Redis 重启） |
| 用户等待 | 0（直接返回旧数据） | 排队等重建完成 |
| DB 压力 | 只有 1 个请求去重建 | 只有 1 个请求去重建（关键是**没抢到锁的要等，不能直接查库**） |
| 代价 | 会读到脏数据，持续时间 = 重建耗时 | 请求阻塞，重建慢时会堆积 |

**互斥锁方案里最容易写错的一点**：没抢到锁的请求**不能直接查库**。
如果直接查库，"加锁"就只保护了一个请求，数据库依旧被 N-1 个请求打穿。
本项目的做法是短暂自旋（3 × 50ms）等缓存被填好，超时才降级直查 DB（且**不回写缓存**，避免与持锁者竞争）。

**锁的两个细节**：
- `tryLock(wait, lease, unit)` 指定了 `leaseTime` 就**关闭看门狗**。重建是有界操作，显式 lease 更可控：即使重建线程卡死，10 秒后锁自动释放，不会永久死锁。
- `finally` 里必须 `isHeldByCurrentThread()` 再 `unlock()`。否则锁因超时被释放、又被别的线程拿到时，会**误删他人的锁**。

## 决策 13：防雪崩 —— TTL 抖动

如果所有商品缓存在同一时刻被批量预热，固定 TTL 会让它们在**同一秒集体失效**，
数据库瞬间承受全量回源。

解法：`ttl = base + random(0, base * jitterRatio)`，把失效时刻打散到 `[base, base*1.2]` 区间。

**配套细节**：L2 的**物理 TTL（30min）必须显著大于逻辑过期时间（3min）**。
否则逻辑过期还没到，key 就被 Redis 删了，"逻辑过期"方案直接失效退化成缓存穿透。

## 决策 14：防穿透 —— 三层缺一不可

| 层 | 手段 | 拦住什么 | 局限 |
|---|---|---|---|
| 0 | 参数校验（`id <= 0` 直接拒绝） | 最粗糙的扫描 | 只能拦非法格式 |
| 1 | 布隆过滤器（Redis Bitmap） | **一定不存在**的 ID | 有误判率；**不支持删除**（商品下架后 ID 仍在） |
| 2 | 空值缓存（短 TTL 60s） | 布隆放过的误判流量 + 已删除商品 | 占用内存；新商品创建后必须清掉 |

**为什么三层都要**：布隆过滤器不支持删除，所以商品下架后查它仍会"可能存在"，
必须靠空值缓存兜住。**空值缓存的副作用是"新商品可能查不到"，所以写路径上必须清空值缓存**——
这个细节很容易漏，本项目在 `ProductService.create` 和 `writeCache` 里都做了。

**为什么用 Redis 布隆过滤器而不是 Guava**：本地版本每个实例各存一份，多实例需要同步、重启就丢。
Redis 版本所有实例共享同一份判断。在本项目里这个网络往返被 L1 挡住了，实际影响可忽略。

## 决策 15：限流算法 —— 滑动窗口 + 令牌桶并用

| | 滑动窗口（ZSET） | 令牌桶（HASH） |
|---|---|---|
| 内存 | O(窗口内请求数)，每个请求约 100 字节 | **O(1)**（两个字段） |
| 突发流量 | 严格削峰，会把正常突发也打散 | 允许攒令牌，天然支持突发 |
| 精度 | 严格限制"任意 window 内的请求数" | 限制"长期平均速率 + 突发上限" |

**滑动窗口解决的经典缺陷**：固定窗口（INCR + EXPIRE）在边界会被打穿——
第 1 秒最后 10ms 打 100 个、第 2 秒最初 10ms 再打 100 个，2 秒内实际放过了 200 个，而配置是"每秒 100"。

**本项目按接口的真实成本分配算法**：
- **秒杀接口** → 滑动窗口（要的就是严格削峰），阈值 5/s
- **登录接口** → 令牌桶（正常用户偶尔连点几下不该被拒），容量 10、速率 0.5/s

**被拒绝的请求不写入 ZSET**：否则持续压测会不断把窗口"续命"，
既会把攻击者自己锁死，也会让 ZSET 无限膨胀。本项目有专门的测试断言这一点。

**IP 维度不可信（安全提示）**：`X-Forwarded-For` 是客户端可伪造的，攻击者每次换一个假 IP 就能绕过按 IP 限流。
所以本项目所有限流策略里**一定会同时开启 USER 维度**——按 IP 限流只能挡最粗糙的攻击，不能作为唯一防线。

## 决策 16：限流降级用 fail-open，不用 fail-close

Redis 挂掉时限流判定会抛异常。此时：

- **fail-close（拒绝所有）**：等于"限流组件故障 → 全站不可用"，把一次局部故障放大成全局事故。
- **fail-open（放行）选用**：记 WARN + 打 `mall.rate.limit.degraded` 指标，把决定权交还给下游自身的容量上限（连接池、线程池都有各自的上界）。

**什么时候该用 fail-close**：接口本身极其脆弱（比如会打挂数据库的慢查询），
此时放行等于把数据库也一起拖死。本项目把 `fail-open` 做成配置项，可按接口切换。

## 决策 17：JWT 黑名单 vs 白名单

| | 黑名单（选用，简历描述一致） | 白名单（jti 存 `auth:user:jti:{userId}`） |
|---|---|---|
| 每次请求成本 | 1 次 Redis GET | 1 次 Redis GET |
| 主动退出 | 把 jti 写进黑名单 | DEL 该 key |
| 单点登录 / 踢人 | 需要额外机制 | **天然支持** |
| key 数量 | 登出次数 × token 有效期 | 与用户数同阶 |

**黑名单的关键设计：TTL 取 token 剩余有效期，而不是固定值。**
黑名单 key 的意义只到"这个 token 本来就会过期"为止。这样它的容量上限被牢牢钉在
`登出速率 × token 有效期`，永远不会无限增长——这是这个方案能上生产的关键。

**JWT 本身的几个坑（本项目都处理了）**：
1. **只放 userId / username / jti**，不放权限和敏感信息。payload 只是 Base64，不是加密。
2. **必须带 jti**，否则没法精确拉黑单个令牌，退出只能退化成"改密钥让全站 token 失效"。
3. **算法显式指定**。JWT 最经典的漏洞是 alg 混淆攻击（header 改成 `{"alg":"none"}`），解析侧用 `verifyWith(key)` 固定密钥，两端都不接受 header 自称的算法。
4. **校验 issuer + 时钟偏移**。前者防止别的系统用同一个 secret 签的 token 混进来，后者避免多实例机器时间差几秒就误判过期。

## 决策 18：订单状态流转用条件更新，不用"先查再改"

```sql
-- ✅ 判断与修改压进同一条语句，由 InnoDB 行锁保证互斥
UPDATE t_order SET status = 2, cancel_time = ? WHERE order_no = ? AND status = 0
-- 影响行数 = 1 → 本次真正完成了流转；= 0 → 状态已变更

-- ❌ 两步之间有窗口，支付回调与超时关单可能同时通过判断
Order o = select(orderNo);
if (o.status == CREATED) { update(...); }
```

**库存回补挂在"取消成功"的分支上**：只有影响行数为 1 才回补。
这样"超时关单 / 用户取消 / 兜底扫描"三条路径并发触发时也只会回补一次，
**幂等性由数据库状态机保证，而不是靠应用层加锁**。

**⚠️ 一个真实的坑：MySQL Connector/J 的 `useAffectedRows`**
默认值 `false` 会让驱动带上 `CLIENT_FOUND_ROWS` 标志，
使 UPDATE 返回的是**匹配行数**而不是**实际变更行数**，进而让"靠影响行数判断是否抢到"的写法在边界情况下失真。
本项目在 JDBC URL 里显式设置了 `useAffectedRows=true`。

## 决策 19：主键 —— 交易类表用雪花，配置类表用自增

| | 自增 | 雪花 ID |
|---|---|---|
| 写入性能 | 高并发插入有 **AUTO-INC 锁竞争** | 无锁，本地生成 |
| B+ 树局部性 | 完美递增 | 趋势递增（同机器号内递增） |
| 分库分表 | **无法全局唯一** | 天然全局唯一 |
| 可读性 / 安全性 | 暴露业务量（竞对能估算日订单量） | 不暴露 |

**本项目的划分**：用户 / 商品 / 活动（写少读多，运营创建）用自增；
订单 / 订单项 / 消息 / 库存流水（高并发写入）用雪花。

**为什么订单号不用"时间戳 + 随机数"**：随机数在极高并发下存在碰撞概率，
而 `uk_order_no` 一旦冲突，会在消费端表现为"订单唯一键冲突"，被误判成重复抢购，非常难排查。

## 决策 20：为什么 Redis 操作用 `StringRedisTemplate` + 自研 JSON，不用 `RedisTemplate<String,Object>`

| 序列化器 | 问题 |
|---|---|
| `JdkSerializationRedisSerializer`（默认） | 二进制，`redis-cli get` 全是乱码，线上排查基本靠猜；且存在反序列化漏洞面 |
| `GenericJackson2JsonRedisSerializer` | 会往 JSON 里写 `@class` 全限定类名——类改名/挪包后历史缓存全部反序列化失败；同时把安全边界交给"反序列化任意类" |
| **`StringRedisTemplate` + `JsonUtils`（选用）** | 存的是 UTF-8 JSON，`redis-cli` 一眼能看懂；序列化行为由一处决定，不会出现"写进去能读出来、换个序列化器就读不出来" |

## 决策 21：什么场景**不该**用这套架构

这是最容易被面试官认可的一段"自我批判"：

| 场景 | 应该怎么做 | 用本方案的问题 |
|---|---|---|
| 日订单量几千的普通电商 | 同步落库 + 简单缓存 | 引入 MQ/补偿/对账，复杂度远超收益 |
| 库存不紧张的常规商品 | 数据库乐观锁就够了 | Redis 库存是多余的一层，还多了一致性问题 |
| 强一致要求的金融交易 | 数据库事务 + TCC/SAGA | "最终一致"不可接受 |
| 秒杀商品只有几十件 | 数据库行锁直接扛 | Redis + MQ 的链路开销比数据库还大 |
| 团队没有 MQ 运维能力 | 用数据库轮询表 | 引入了没人能维护的组件 |

**判断标准**：只有当"瞬时并发量级 × 可接受的延迟"远超数据库能力，且业务能接受最终一致时，这套架构才划算。
